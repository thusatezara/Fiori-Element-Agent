# 기능 명세: Fiori 애플리케이션 요청 유형 판정

**Feature Branch**: `001-classify-fiori-app-request`

**Created**: 2026-09-08

**Last Updated**: 2026-09-08

**Status**: Draft

**Input**: User description: "Fiori 기술 용어를 모르는 사용자의 업무 요청을 대화로 구체화하고 확인된 서비스 정보와 함께 분석하여 Standard, Custom 또는 FreeStyle 중 적합한 생성 유형을 추천한 뒤, 사용자의 승인을 받아 해당 생성 기능에 전달한다."

## 사용자 시나리오 및 테스트 *(필수)*

### 사용자 스토리 1 - 비기술적 업무 요청의 앱 유형 추천 (Priority: P1)

SAP 애플리케이션 개발자 또는 업무 전문가는 만들려는 화면과 업무를 일상적인 표현으로 설명하고, 적합한 앱 유형과 이해 가능한 추천 이유를 받는다.

**우선순위 이유**: 사용자가 Fiori 기술 용어를 모르더라도 후속 설계의 올바른 출발점을 얻는 것이 가장 기본적인 가치다.

**독립 테스트**: `STD-01`, `CUS-01`, `FRE-01`의 비기술적 요청을 각각 제출하여 추가 기술 선택을 요구하지 않고 기대 유형 하나와 업무 표현의 추천 이유가 제시되는지 검증한다.

**인수 시나리오**:

1. **Given** 사용자가 여러 건을 검색·필터링하고 한 건을 선택해 상세에서 확인·수정하는 일반적인 흐름을 원하며 별도의 특수 화면이나 직접 제어 동작은 필요하지 않다고 설명했을 때, **When** 요청을 판정하면, **Then** `STANDARD`를 추천하고 사용자 진술과 확인된 서비스 근거를 설명한다.
2. **Given** 사용자가 정해진 목록·상세 흐름과 다른 화면 배치를 원하지만 metadata 기반 표준 필드·필터·테이블의 의미와 동작은 재사용할 수 있는 요구를 설명했을 때, **When** 요청을 판정하면, **Then** `CUSTOM`을 추천하고 독립 View가 필요한 이유를 사용자가 이해할 수 있는 말로 설명한다.
3. **Given** 사용자가 여러 단계의 동적 화면, 복잡한 client 상태 또는 화면 흐름의 직접 제어를 요구하고 metadata 기반 화면 구성을 원하지 않을 때, **When** 요청을 판정하면, **Then** `FREESTYLE`을 추천하고 Standard 또는 Custom으로 충족하기 어려운 이유를 설명한다.
4. **Given** 서비스 정보에서 확인할 수 있는 데이터 구조나 capability가 있을 때, **When** 요청을 판정하면, **Then** 시스템은 사용자에게 같은 사실을 묻지 않고 확인된 정보를 근거로 사용한다.

---

### 사용자 스토리 2 - 불충분하거나 충돌하는 요청 구체화 (Priority: P2)

사용자는 앱 유형을 결정하기에 부족하거나 서로 충돌하는 요청을 제출한 뒤, 기술 용어가 아닌 업무 질문에 답하여 임의 판정 없이 요구사항을 구체화한다.

**우선순위 이유**: 실제 초기 요청은 짧고 모호한 경우가 많으므로 잘못된 유형을 선택하지 않고 대화를 통해 결정 가능 상태로 만드는 가치가 필요하다.

**독립 테스트**: `INS-01`, `AMB-01`, `AMB-02`를 각각 제출하고 답변이 부족한 동안 미결정 상태가 유지되며, 필요한 질문에 충분히 답한 뒤 정확히 하나의 추천으로 바뀌는지 검증한다.

**인수 시나리오**:

1. **Given** 사용자가 "업무 데이터를 조회하고 수정하는 화면"처럼 기술 유형을 특정하지 않은 요청을 제공했을 때, **When** 현재 정보만으로 앱 유형을 결정할 수 없으면, **Then** 시스템은 목록·상세·수정 방식처럼 판정에 필요한 업무 질문을 기술 용어 없이 제시한다.
2. **Given** 하나의 요청에 서로 다른 앱 유형을 가리키는 요구사항이 함께 있을 때, **When** 요청을 판정하면, **Then** 시스템은 임의로 우선순위를 정하지 않고 충돌 항목과 결정을 위해 필요한 업무 질문을 제시한다.
3. **Given** 사용자의 답변이 판정에 충분하지 않을 때, **When** 요청을 다시 판정하면, **Then** 시스템은 하나의 유형을 강제로 선택하지 않고 남은 미결정 사항에 대해서만 추가 질문한다.
4. **Given** 사용자가 판정에 충분한 답변을 제공했을 때, **When** 요청을 다시 판정하면, **Then** 답변을 판정 근거에 포함하고 하나의 유형을 추천한다.

---

### 사용자 스토리 3 - 판정 검토·승인 및 생성 요청 전달 (Priority: P3)

사용자는 추천된 유형, 근거와 준비 조건을 검토하고 승인한 뒤, 자신의 원문 요구사항이 보존된 하나의 생성 요청으로 전달되게 한다.

**우선순위 이유**: 추천 결과를 통제 가능한 생성 입력으로 전환해야 사용자의 의도와 승인 없이 잘못된 프로젝트가 만들어지는 일을 막을 수 있다.

**독립 테스트**: 미리 준비한 완전한 `CUSTOM` 판정 결과를 사용하여 미승인 상태에서는 생성 요청이 전달되지 않고, 승인 후에는 원문과 근거를 보존한 Custom 생성 요청 하나만 전달되는지 검증한다.

**인수 시나리오**:

1. **Given** 필요한 backend capability를 서비스 정보에서 확인할 수 없을 때, **When** 사용자가 판정 결과를 검토하면, **Then** 앱 유형과 생성 준비 상태를 구분하고 누락된 capability를 backend 선행 조건으로 확인할 수 있다.
2. **Given** 하나의 유형이 추천되었을 때, **When** 사용자가 판정 결과를 검토하면, **Then** 업무 표현으로 된 추천 설명과 후속 생성 기능을 위한 기술적 handoff 정보를 함께 확인할 수 있다.
3. **Given** 판정 결과가 아직 승인되지 않았을 때, **When** 시스템이 프로젝트 생성 가능 여부를 결정하면, **Then** 생성 대기 상태를 유지하고 어떤 생성 진입점도 실행하지 않는다.
4. **Given** 사용자가 완전한 판정 결과를 승인했을 때, **When** 시스템이 후속 생성 요청을 전달하면, **Then** 승인된 유형에 해당하는 정확히 하나의 생성 진입점으로 원문 요구사항, 사용자 답변, 판정 근거와 선행 조건을 전달한다.

### 비규범적 예시 대화

> 다음 대화는 판정 과정을 이해하기 위한 예시일 뿐이며, 이 Feature의 생성 대상이나 지원 업무 도메인을 이상사례 관리로 제한하지 않는다.

**Q**: 이상사례를 조회하고 수정하는 화면을 만들자.

**A**: 여러 건을 목록에서 찾은 후 한 건을 선택해 수정하는 방식인가요?

**Q**: 그래. Table 구조로 만들어줘. 데이터는 1,000건이 넘고 주로 PC에서 많은 열을 확인할 거야.

**판정 예시**: 일반적인 목록·상세 흐름이므로 `STANDARD` 후보이며, table 유형과 수정 방식은 사용 환경 및 service capability를 함께 확인한 후 Standard 생성 단계에서 결정한다.

### Edge Cases

- 사용자가 기술 유형을 직접 지정해도 업무 요구사항과 충돌하면 그대로 확정하지 않고 충돌과 영향을 설명한다.
- `table`, `수정`, 예상 행 수처럼 하나의 신호만으로 앱 유형이나 Extension 필요 여부를 확정하지 않는다.
- 하나의 요청에 서로 다른 진입점이 필요한 복수 앱이 포함되면 단일 유형으로 축약하지 않고 앱별 요청 분리를 안내한다.
- 질문으로 확인할 수 있는 사용자 선호와 서비스 정보에서 검증해야 하는 사실을 구분한다.
- 동일한 질문에 앞서 받은 답변이 있으면 반복해서 묻지 않는다.
- metadata에 없는 property, association, action 또는 capability를 존재하는 것으로 추측하지 않는다.
- Standard, Custom, FreeStyle 어느 쪽으로도 충족할 수 없는 backend 변경은 별도 선행 조건으로 분리한다.
- 재판정 중 원문 요구사항이나 사용자 답변이 누락되거나 의미가 바뀌면 승인 가능한 결과로 표시하지 않는다.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 시스템은 사용자가 Fiori 기술 용어를 사용하지 않아도 업무 목표, 화면에서 할 일, 대상 데이터, 사용자 동작과 사용 환경을 요청으로 받아야 한다.
- **FR-002**: 시스템은 원문 요청과 후속 답변을 각각 식별 가능한 요구사항으로 보존하고 판정 결과까지 추적할 수 있어야 한다.
- **FR-003**: 시스템은 사용자에게 기술 유형을 직접 선택하도록 요구하기 전에 업무 흐름과 화면 동작에서 판정 근거를 추출해야 한다.
- **FR-004**: 시스템은 유형 판정에 꼭 필요한 정보가 없을 때만 추가 질문하고, 질문의 목적과 선택에 따른 차이를 사용자가 이해할 수 있는 표현으로 설명해야 한다.
- **FR-005**: 시스템은 이미 제공된 답변이나 서비스 정보에서 확인할 수 있는 사실을 반복 질문해서는 안 된다.
- **FR-006**: 시스템은 명확한 답변이 나올 때까지 미결정 상태를 유지할 수 있어야 하며 부족한 정보로 유형을 강제 확정해서는 안 된다.
- **FR-007**: 시스템은 사용자 진술, 시스템이 해석한 판단과 서비스 정보로 확인한 사실을 판정 결과에서 구분해야 한다.
- **FR-008**: 시스템은 목록·검색·필터·상세·일반적인 생성·수정 흐름을 metadata 기반 표준 화면으로 충족할 수 있고 별도 View나 직접 제어가 필요하지 않으면 `STANDARD`를 우선 추천해야 한다.
- **FR-009**: 시스템은 별도 View와 고유한 화면 배치가 필요하지만 metadata 기반 표준 화면 요소와 의미를 재사용할 수 있으면 `CUSTOM`을 추천해야 한다.
- **FR-010**: 시스템은 복잡한 화면 상태와 interaction을 직접 제어해야 하고 metadata 기반 화면 구성에 의존하지 않아야 하면 `FREESTYLE`을 추천해야 한다.
- **FR-011**: 시스템은 Standard로 충족할 수 있는 요구사항에 Custom 또는 FreeStyle을 추천해서는 안 되며, Custom으로 충족할 수 있는 요구사항에 FreeStyle을 추천하려면 그 필요성을 설명해야 한다.
- **FR-012**: 시스템은 table 사용 여부, 전체 데이터 행 수 또는 수정 요구 하나만으로 앱 유형, table 유형 또는 Extension 필요 여부를 확정해서는 안 된다.
- **FR-013**: 시스템은 앱 유형, 세부 화면 구성과 table·수정 방식, Extension 필요 여부 및 backend 준비 상태를 서로 다른 판정 항목으로 구분해야 한다.
- **FR-014**: 시스템은 서비스 정보에서 확인되지 않은 EntitySet, property, association, action, annotation 또는 capability를 존재하는 것으로 추측해서는 안 된다.
- **FR-015**: 시스템은 앱 유형과 별개로 누락된 backend capability를 생성 선행 조건으로 표시해야 한다.
- **FR-016**: 시스템은 판정 결과에 선택 유형, 사용자용 설명, 기술적 근거, 요구사항별 분류, 미결정 사항, backend 선행 조건과 후속 생성 기능을 포함해야 한다.
- **FR-017**: 시스템은 사용자가 판정 결과를 승인하기 전에는 어떤 프로젝트 생성 기능도 실행해서는 안 된다.
- **FR-018**: 시스템은 승인된 판정 결과를 정확히 하나의 생성 유형에 연결해야 한다.
- **FR-019**: 시스템은 후속 생성 요청에 원문 요구사항, 사용자 답변, 판정 근거와 선행 조건을 손실 없이 전달해야 한다.
- **FR-020**: 시스템은 하나의 요청에 복수 앱이 필요한 경우 앱별로 독립 판정할 수 있도록 요청 분리를 안내해야 한다.
- **FR-021**: 시스템은 이 Feature에서 Standard, Custom 또는 FreeStyle 프로젝트 파일을 생성하지 않아야 한다.

### 주요 정보 객체 *(Key Entities)*

> 이 절의 객체는 DB table이나 OData EntityType을 뜻하지 않는다. 기능이 생성, 참조 또는 전달하는 주요 정보를 정의하며 저장 방식은 Plan에서 결정한다.

- **원문 업무 요청**: 사용자가 만들고 싶은 업무, 화면, 데이터와 동작을 자신의 표현으로 설명한 입력이다.
- **확인 질문과 답변**: 유형 판정에 필요한 미결정 사항을 해소하기 위한 질문, 사용자 답변과 그 이유다.
- **서비스 설명**: 외부 서비스에서 확인한 EntitySet, property, association, action, annotation 및 capability이며 이 Feature가 소유하거나 변경하지 않는다.
- **판정 근거**: 사용자 진술, 시스템 판단과 서비스에서 확인한 사실을 구분하여 유형 결정에 연결한 정보다.
- **앱 유형 판정**: `STANDARD`, `CUSTOM`, `FREESTYLE` 또는 미결정 상태와 추천 이유다.
- **생성 준비 상태**: 후속 생성 가능 여부와 미결정 사항 또는 backend 선행 조건이다.
- **승인된 생성 요청**: 정확히 하나의 유형, 원문 요구사항, 답변, 판정 근거와 선행 조건을 보존한 handoff 결과다.

## 성공 기준 *(필수)*

### 대표 검증 사례

| ID | 비기술적 요청 또는 상황 | 기대 결과 |
|---|---|---|
| `STD-01` | 데이터를 검색·필터링하고 한 건을 선택해 상세에서 일반적인 방식으로 수정 | `STANDARD` 추천 |
| `STD-02` | 데이터를 목록과 상세 화면에서 조회하며 별도 특수 화면이나 직접 제어 불필요 | `STANDARD` 추천 |
| `CUS-01` | 정해진 목록·상세 흐름과 다른 업무 화면 배치가 필요하지만 표준 필드·필터·테이블 의미는 재사용 가능 | `CUSTOM` 추천 |
| `CUS-02` | 하나의 고유한 업무 화면 안에 검색 조건, 테이블과 상세 영역을 원하는 위치에 조합 | `CUSTOM` 추천 |
| `FRE-01` | 여러 단계 입력에 따라 다음 화면과 control이 동적으로 바뀌고 client 상태를 직접 관리 | `FREESTYLE` 추천 |
| `FRE-02` | metadata 기반 화면 구성을 사용하지 않고 복잡한 화면 흐름과 interaction을 직접 정의 | `FREESTYLE` 추천 |
| `AMB-01` | 목록 중심의 일반 흐름과 독립적인 특수 시작 화면을 동시에 요구하지만 우선순위 미제공 | 미결정 유지 및 시작 흐름 질문 |
| `AMB-02` | 표준 화면 요소 재사용을 원하면서 metadata 기반 화면 구성은 전혀 사용하지 않겠다고 요청 | 충돌 설명 및 우선 조건 질문 |
| `INS-01` | "업무 데이터를 조회하고 수정"한다는 목적만 제공 | 목록·상세·수정 방식에 대한 비기술적 질문 |
| `BACKEND-01` | 승인 동작이 필요하지만 서비스에서 승인 capability를 확인할 수 없음 | 추천 유형과 별도로 backend 선행 조건 표시 |
| `MULTI-01` | 목록 조회 앱과 별도의 복잡한 관리 앱을 하나의 요청에 포함 | 앱별 요청 분리 안내 |
| `APPROVAL-01` | 유형은 추천됐으나 사용자가 아직 승인하지 않음 | 어떤 생성 진입점도 실행하지 않음 |
| `APPROVAL-02` | `CUSTOM` 판정과 근거를 사용자가 승인 | Custom 생성 진입점 하나만 가리키는 handoff |
| `TRACE-01` | 유형 신호, backend 조건과 범위 밖 요구가 섞인 요청 | 모든 원문 요구사항을 결과에서 분류·추적 |

### 측정 가능한 결과

- **SC-001**: `STD-01`~`FRE-02`의 6개 기준 사례 100%에서 기대 유형과 일치하는 추천이 제공된다.
- **SC-002**: `AMB-01`, `AMB-02`, `INS-01`의 3개 불충분·충돌 사례 100%에서 임의 유형 확정 없이 사용자 결정에 필요한 질문이 제시된다.
- **SC-003**: `TRACE-01`을 포함한 모든 기준 사례에서 제출된 원문 요구사항과 사용자 답변의 100%가 판정 근거, 선행 조건, 미결정 또는 범위 밖 중 하나로 추적된다.
- **SC-004**: `APPROVAL-01`을 포함한 모든 미승인 사례의 100%에서 프로젝트 생성 진입점이 실행되지 않는다.
- **SC-005**: `APPROVAL-02`를 포함한 모든 승인 사례의 100%가 정확히 하나의 생성 유형을 가리키고 원문 요구사항과 판정 근거를 보존한다.
- **SC-006**: 대상 SAP 개발자 또는 업무 전문가 5명 이상을 대상으로 한 사용성 검증에서 참여자의 80% 이상이 기술 용어 설명 없이 판정 질문에 답하고, 결과 표시 후 30초 이내에 추천 이유와 다음 결정을 올바르게 설명한다.
- **SC-007**: 서비스 정보로 확인 가능한 사실을 사용자에게 다시 묻는 기준 사례는 0건이다.

## 가정 및 의존성

- 초기 지원 유형은 `STANDARD`, `CUSTOM`, `FREESTYLE` 세 가지다.
- 사용자는 Fiori elements, Building Blocks, annotation, MVC 또는 table control 이름을 알지 못할 수 있다.
- Standard는 List Report target과 metadata·annotation 중심 구성, Custom은 별도 View target과 Building Blocks 및 annotation 활용, FreeStyle은 annotation을 화면 구성에 사용하지 않는 MVC 구성으로 정의한다.
- 하나의 자연스러운 대화 안에서 `001`의 유형 판정 후 선택된 `002`, `003` 또는 `004`의 세부 질문으로 이어질 수 있다.
- 판정 입력에 필요한 서비스 정보는 접근 가능한 형태로 제공되며 확인할 수 없는 내용은 선행 조건으로 남긴다.
- 실제 프로젝트 생성, table 유형과 상세 수정 방식 같은 유형별 세부 결정은 후속 생성 Spec이 담당한다.
- 인증, backend 변경, 배포와 운영 요구사항은 별도 Feature로 다룬다.

## 범위 제외

- Standard, Custom 또는 FreeStyle 프로젝트 파일 생성
- table 유형, 상세 화면 구성이나 Extension 구현의 최종 결정
- backend 서비스와 업무 규칙 생성 또는 변경
- 기존 애플리케이션 수정과 migration
- 실제 배포 또는 SAP 시스템 변경
- 다중 사용자 실행, queue, 보존 정책 및 운영자 기능
