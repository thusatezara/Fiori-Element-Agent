## 사용자 입력

```text
$ARGUMENTS
```

진행하기 전에 **반드시** 사용자 입력을 고려해야 합니다(비어 있지 않은 경우).

## 실행 전 검사

**확장 후크 확인(수렴 전)**:

- 프로젝트 루트에 `.specify/extensions.yml`가 존재하는지 확인하세요.
- 존재하는 경우 이를 읽고 `hooks.before_converge` 키 아래 항목을 찾습니다.
- YAML을 파싱할 수 없거나 유효하지 않은 경우 후크 검사를 자동으로 건너뛰고 정상적으로 계속 진행합니다.
- `enabled`가 명시적으로 `false`인 후크를 필터링합니다. `enabled` 필드가 없는 후크는 기본적으로 활성화된 것으로 처리합니다.
- 나머지 각 후크에 대해 후크 `condition` 표현식을 해석하거나 평가하려고 **하지 마세요**.
- 후크에 `condition` 필드가 없거나 null/empty인 경우 후크를 실행 가능한 것으로 처리합니다.
- 후크가 비어 있지 않은 `condition`를 정의하는 경우 후크를 건너뛰고 조건 평가를 HookExecutor 구현에 맡깁니다.
- 후크 명령 이름으로 명령 호출을 구성할 때 점(`.`)을 하이픈(`-`)으로 바꾸십시오. 예를 들어 `speckit.git.commit` → `$speckit-git-commit`입니다.
- 각 실행 가능한 후크에 대해 `optional` 플래그를 기반으로 다음을 출력합니다.
- **후크 옵션**(`optional: true`):

    ```text
## 확장 후크

**옵션 프리훅**: {extension}
명령: `/{command}`
설명: {description}

프롬프트: {prompt}
실행하려면: `/{command}`
    ```

- **필수 후크** (`optional: false`):

    ```text
## 확장 후크

**자동 프리훅**: {extension}
실행 중: `/{command}`
EXECUTE_COMMAND: {command}

목표로 진행하기 전에 후크 명령의 결과를 기다리세요.
    ```
위의 블록을 출력한 후에는 실제로 후크를 호출하고 계속하기 전에 완료될 때까지 기다려야 합니다. 이 에이전트/세션에서 직접 명령을 실행하는 것과 동일한 방식으로 실행합니다(호출은 위에 표시된 리터럴 `{command}` ID와 다를 수 있습니다. 예를 들어 기술 모드 에이전트는 이를 `/skill:speckit-...` 또는 `$speckit-...`로 실행합니다). 블록을 출력하는 것만으로는 후크가 실행되지 않습니다.

- 등록된 Hook이 없거나 `.specify/extensions.yml`가 존재하지 않는 경우 자동으로 건너뜁니다.

## 목표

기능의 사양, 계획, 작업이 요구하는 것과 요구되는 것 사이의 격차를 줄입니다.
코드베이스는 현재 구현됩니다. ** 단독으로 `spec.md`, `plan.md` 및 `tasks.md`를 읽으십시오.
의도의 근원**(헌법을 지배 제약으로 삼음), 현재를 평가합니다.
코드 상태, 요구 사항, 수용 기준, 계획 결정 등을 결정합니다.
기존 작업이 충족되지 않거나 불완전하거나 부분적으로만 만족되고 **각 부분을 추가합니다.
남은 작업은 `tasks.md` 하단에 추적 가능한 새로운 작업**으로 남아 있습니다.
`$speckit-implement`는 그것을 완료할 수 있습니다. 이 명령은 다음 이후에만 실행되어야 합니다.
`$speckit-implement`는 현재 `tasks.md`에서 실행되었으며 `$speckit-tasks`가 완전한 `tasks.md`를 생성한 후입니다.

이것은 diff 도구가 **아닙니다** 변경 사항을 추적하지 **않습니다**. 현재 상태를 평가합니다.
기능의 아티팩트와 관련된 코드 — git 없음, 분기 비교 없음, 기록 없음.

## 운영 제약

**APPEND-ONLY, NEVER REWRITE**: 명령의 **유일한** 쓰기는 새 항목을 추가합니다.
`## Phase N: Convergence` 섹션을 `tasks.md`로 변경합니다. 다음과 같은 행위는 해서는 안 됩니다:

- 어떤 방식으로든 `spec.md` 또는 `plan.md`를 수정합니다.
- 기존 작업을 다시 작성, 번호 다시 매기기, 순서 변경 또는 삭제합니다(이전 작업 포함).
수렴 단계);
- 애플리케이션 코드를 수정, 생성 또는 삭제합니다. 추가된 작업을 완료하는 것이
`$speckit-implement`의 작업입니다.

코드베이스가 이미 모든 것을 만족하면 명령은 `tasks.md`를 떠나야 합니다.
**바이트 단위로 변경되지 않음**(빈 Convergence 헤더 없음) 및 깨끗한 결과를 보고합니다.

**헌법기관**: 프로젝트 구성(`.specify/memory/constitution.md`)은 다음과 같습니다.
**협상 불가능**. MUST 원칙을 위반하는 코드는 심각도가 가장 높은 결과이며
해당 수정 작업을 생성합니다. 헌법이 채워지지 않은 템플릿인 경우,
실패하기보다는 건강 상태 확인을 우아하게 건너뛰세요.

## 실행 단계

### 1. 융합컨텍스트 초기화

repo 루트에서 `.specify/scripts/powershell/check-prerequisites.ps1 -Json -RequireSpec -RequireTasks -IncludeTasks`를 한 번 실행하고 FEATURE_DIR 및 AVAILABLE_DOCS에 대해 JSON을 구문 분석합니다. 절대 경로 파생:

- SPEC = FEATURE_DIR/spec.md
- PLAN = FEATURE_DIR/plan.md
- TASKS = FEATURE_DIR/tasks.md
- CONSTITUTION = `.specify/memory/constitution.md` (존재하는 경우)
`spec.md`, `plan.md` 또는 `tasks.md`가 누락된 경우 명확하고 실행 가능한 메시지로 중지하세요.
실행하기 위한 필수 명령(사양이 누락된 경우 `$speckit-specify`, 계획이 누락된 경우 `$speckit-plan`,
누락된 작업의 경우 `$speckit-tasks`). 부분 출력을 생성하지 마십시오.
"I'm Groot"와 같이 인수에 작은따옴표를 사용하려면 이스케이프 구문을 사용하세요. 예: 'I'\''m Groot'(또는 가능하면 큰따옴표: "I'm Groot").

### 2. 아티팩트 로드(점진적 공개)

각 아티팩트에서 필요한 최소한의 컨텍스트만 로드합니다.

**spec.md에서:**

- 기능 요구 사항(FR-###)
- 성공 기준(SC-###) — 구축 가능한 작업이 필요한 항목만 포함합니다. 제외하다
출시 후 결과 지표 및 비즈니스 KPI
- 사용자 스토리 및 승인 시나리오
- 엣지 케이스(있는 경우)

**plan.md에서:**

- Architecture/stack 선택 및 기술적 결정
- 데이터 모델 참조
- 단계 및 명명된 터치 포인트(계획에 files/components가 생성되거나 편집될 것이라고 명시되어 있음)
- 기술적 제약

**tasks.md에서:**

- 작업 ID(다음 ID 및 다음 단계 번호를 계산하기 위해)
- 설명, 단계 그룹화 및 참조 파일 경로

**구성에서(채워지지 않은 템플릿이 아닌 경우):**

- 원리명 및 MUST/SHOULD 규범문

### 3. 인텐트 인벤토리 구축

내부 모델을 만듭니다(원시 아티팩트를 에코하지 않음).

- **요구 사항 인벤토리**: FR-### / SC-### / 사용자 스토리 승인당 안정적인 키 1개
시나리오(예: `US1/AC2`), 계획 결정 및 구성 원칙
구축 가능한 의무를 부과합니다.
- **코드 범위 맵**: `plan.md` 및 `tasks.md`에 명명된 파일 경로와 키워드에서
각 요구사항이 설명하는 개념을 검색하고 소스 파일 세트를 파생시키며
평가 범위에 있는 구성요소. 평가를 다음과 같이 제한합니다. 추론하지 **않습니다**
아티팩트가 정의하는 것 이상의 범위.

### 4. 코드베이스를 평가하고 결과를 분류합니다.

인텐트 인벤토리의 각 항목에 대해 범위 내 현재 코드를 검사하고
`Finding`는 틈이 있는 곳에만 해당됩니다. **간격 유형**별로 모든 결과를 분류합니다.

- **`missing`**: 필요한 작업이 코드에 전혀 없습니다.
- **`partial`**: 저작물이 존재하지만 아직 요구사항을 완전히 충족하지 않습니다. /
수용 기준/계획 결정.
- **`contradicts`**: 코드가 명시된 의도와 충돌하는 작업을 수행하거나
헌법은 원칙을 지켜야 한다.
- **`unrequested`**: 코드에 사양, 계획 또는 작업에서 요구하지 않은 작업이 포함되어 있습니다.
(인식을 위해 표시됨 - 수렴은 코드를 삭제하지 **않고** 작업을 추가하기만 함)
review/justify 또는 제거).

각 `Finding`는 안정적인 ID, 추적 대상인 `source-ref`, `gap-type`,
심각도, 사람이 읽을 수 있는 짧은 설명과 증거(file/area 관찰)가 포함됩니다.

**최첨단 사례:**

- **아직 코드가 거의 또는 전혀 없음**: 지정된 전체 범위를 `missing` 남은 작업으로 처리합니다.
실패보다는.
- **아무것도 남지 않음**: 결과가 0개이고 7단계의 수렴 분기를 따릅니다.

### 5. 심각도 할당

- **중요**: 헌법 MUST 원칙을 위반하거나 `missing`/`contradicts` 간격을 위반합니다.
이는 P1 사용자 스토리의 기본 기능을 차단합니다.
- **높음**: 핵심 기능 요구 사항 또는 수용에 대한 `missing` 또는 `partial` 격차
기준.
- **중간**: 2차 요구 사항에 대한 `partial` 간격 또는 다음을 포함하는 `unrequested` 추가
불명확한 정당성.
- **낮음**: 사소한 부분적 간격, 광택 또는 위험도가 낮은 `unrequested` 추가.

### 6. 세션 중 조사 결과 요약 제시

항목을 추가하기 전에 간단하고 심각도 등급 요약을 출력합니다(아직 파일 쓰기가 없음).

## 융합 연구 결과

| ID | 간격 유형 | 심각도 | 소스 | 증거 | 남은 작업 |
|----|----------|----------|--------|----------|----------------|
| F1 | 누락 | HIGH | FR-008 | 예: tasks.md를 쓸 때 path/to/module.py에서 추가 전용 가드가 감지되지 않았습니다. | 추가 전용 적용 추가 |

**요약 측정항목:**

- 요구사항/허용기준 확인
- 계획 결정 확인
- 헌법 원칙 확인(또는 "건너뛰기 — 템플릿")
- 공백 유형별 조사 결과(누락/부분/모순/요청되지 않음)
- 심각도별 조사 결과

### 7. 융합 작업 추가(또는 보고서 융합)

**실행 가능한 결과가 하나 이상 있는 경우**(`tasks_appended` 결과):

추가 계약에 따라 `tasks.md`의 **끝**에 추가합니다.

1. 기존 작업 ID를 모두 스캔합니다. `M`를 최대값으로 둡니다. 다음 단계 번호 `N` 결정
(가장 높은 기존 단계 + 1).
2. 하나의 새로운 섹션 헤더 `## Phase N: Convergence`를 작성합니다.
3. CRITICAL/HIGH를 먼저 주문한 실행 가능한 결과당 하나의 체크리스트 항목을 내보내고 할당합니다.
0으로 채워진 ID `T{M+1:03d}, T{M+2:03d}, …`:

   ```markdown
- [ ] <source-ref>당 T042 <imperative description>(<gap-type>)
   ```

`<source-ref>`는 작업을 원본으로 추적합니다. `FR-003`, `SC-002`,
`US1/AC2`, `plan: storage decision`, `Constitution II`.

`<gap-type>`는 `missing`, `partial`, `contradicts`, `unrequested` 중 하나입니다.

헌법 위반 작업을 먼저 내보내고 다음과 같이 설명해야 합니다.
`CRITICAL`.
4. 기존 ID를 재사용하거나 번호를 다시 매기지 마십시오. 이전 수렴 단계가 존재하는 경우 새 단계를 추가합니다.
그 아래에 별도의 번호가 붙은 것 - 이전 것을 만지지 마십시오.

**조치 가능한 결과가 없는 경우**(`converged` 결과):

- `tasks.md`를 전혀 수정하지 **않습니다**. 빈 위상 헤더가 없습니다.
- 보고서: **"✅ 컨버지드 — 구현이 사양, 계획 및 작업을 만족합니다."**
- 검사한 내용의 요약 개수를 포함합니다.

### 8. 다음 작업 제공(핸드오프)

- `tasks_appended`에서: 어떤 단계에 얼마나 많은 작업이 추가되었는지 명시하고 권장합니다.
`$speckit-implement`를 실행하여 완료합니다. 후속 조치가 수렴된다는 점에 유의하세요.
run은 남은 항목을 더 적게 찾거나 전혀 찾지 않습니다.
- `converged`: PR 검토/열기를 진행하는 것이 좋습니다. 추가 구현 패스 없음
이 기능의 지정된 범위에 필요합니다.

### 9. 확장 후크 확인

결과 출력 후 프로젝트 루트에 `.specify/extensions.yml`가 존재하는지 확인합니다.

- 존재하는 경우 이를 읽고 `hooks.after_converge` 키 아래 항목을 찾습니다.
- YAML을 파싱할 수 없거나 유효하지 않은 경우 후크 검사를 자동으로 건너뛰고 정상적으로 계속 진행합니다.
- `enabled`가 명시적으로 `false`인 후크를 필터링합니다. `enabled` 필드가 없는 후크는 기본적으로 활성화된 것으로 처리합니다.
- 나머지 각 후크에 대해 후크 `condition` 표현식을 해석하거나 평가하려고 **하지 마세요**.
- 후크에 `condition` 필드가 없거나 null/empty인 경우 후크를 실행 가능한 것으로 처리합니다.
- 후크가 비어 있지 않은 `condition`를 정의하는 경우 후크를 건너뛰고 조건 평가를 HookExecutor 구현에 맡깁니다.
- 상장 전 수렴결과(`converged` 또는 `tasks_appended`) 세션 중 보고
사용자가 선택적 후속 명령을 실행할지 여부를 결정할 수 있습니다.
- 후크 명령 이름으로 명령 호출을 구성할 때 점(`.`)을 하이픈(`-`)으로 바꾸십시오. 예를 들어 `speckit.git.commit` → `$speckit-git-commit`입니다.
- 각 실행 가능한 후크에 대해 `optional` 플래그를 기반으로 다음을 출력합니다.
- **후크 옵션**(`optional: true`):

    ```text
## 확장 후크

**후크 옵션**: {extension}
명령: `/{command}`
    ```
