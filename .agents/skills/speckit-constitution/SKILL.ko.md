## 사용자 입력

```text
$ARGUMENTS
```

진행하기 전에 **반드시** 사용자 입력을 고려해야 합니다(비어 있지 않은 경우).

## 스코프 가드

이 명령의 자체 작업은 프로젝트 구성 자체를 업데이트하는 것으로 제한됩니다. 종속 템플릿
명령은 런타임에 구성을 읽고 여기에서는 수정되지 않습니다.

- 사용자 입력의 모든 부분을 구성 내용 또는 별도의 내용으로 분류하고,
비정부 의도.
- 입력에 기능 구현, 코드 생성, 리팩토링, 빌드 또는
배포 요청을 실행하면 **해서는 안 됩니다**. 대신 지연된 의도로 추출하십시오.
- 애플리케이션 소스 파일, 기능 경로, 기능 경로를 생성, 수정 또는 삭제해서는 **안 됩니다**.
구성 요소, 테스트, 배포 파일 또는 구성과 관련 없는 기타 아티팩트
작업 흐름.
- 지시 내용이 헌법 내용인지 불분명한 경우 사전에 명확한 설명을 요청하십시오.
변화를 만들고 있습니다.
- 구성 업데이트를 완료한 후 연기된 각 항목에 대해 `Next Actions` 섹션을 포함합니다.
의도. 원래 의도를 나열하고 다음과 같은 적절한 후속 Spec Kit 명령을 제안합니다.
호출하지 않고 `$speckit-specify`로 사용합니다.
- 비거버넌스 의도가 없는 경우 `Next Actions` 섹션을 생략합니다.

## 실행 전 검사

**확장 후크 확인(구성 업데이트 전)**:
- 프로젝트 루트에 `.specify/extensions.yml`가 존재하는지 확인하세요.
- 존재하는 경우 이를 읽고 `hooks.before_constitution` 키 아래 항목을 찾습니다.
- YAML을 파싱할 수 없거나 유효하지 않은 경우 후크 검사를 자동으로 건너뛰고 정상적으로 계속 진행합니다.
- `enabled`가 명시적으로 `false`인 후크를 필터링합니다. `enabled` 필드가 없는 후크는 기본적으로 활성화된 것으로 처리합니다.
- 나머지 각 후크에 대해 후크 `condition` 표현식을 해석하거나 평가하려고 **하지 마세요**.
- 후크에 `condition` 필드가 없거나 null/empty인 경우 후크를 실행 가능한 것으로 처리합니다.
- 후크가 비어 있지 않은 `condition`를 정의하는 경우 후크를 건너뛰고 조건 평가를 HookExecutor 구현에 맡깁니다.
- 후크 명령 이름으로 명령 호출을 구성할 때 점(`.`)을 하이픈(`-`)으로 바꾸십시오. 예를 들어 `speckit.git.commit` → `$speckit-git-commit`입니다.
- 각 실행 가능한 후크에 대해 `optional` 플래그를 기반으로 다음을 출력합니다.
- **후크 옵션**(`optional: true`):
    ```
## 확장 후크

**옵션 프리훅**: {extension}
명령: `/{command}`
설명: {description}

프롬프트: {prompt}
실행하려면: `/{command}`
    ```
- **필수 후크** (`optional: false`):
    ```
## 확장 후크

**자동 프리훅**: {extension}
실행 중: `/{command}`
EXECUTE_COMMAND: {command}

개요로 진행하기 전에 후크 명령의 결과를 기다리십시오.
    ```
위의 블록을 출력한 후에는 실제로 후크를 호출하고 계속하기 전에 완료될 때까지 기다려야 합니다. 이 에이전트/세션에서 직접 명령을 실행하는 것과 동일한 방식으로 실행합니다(호출은 위에 표시된 리터럴 `{command}` ID와 다를 수 있습니다. 예를 들어 기술 모드 에이전트는 이를 `/skill:speckit-...` 또는 `$speckit-...`로 실행합니다). 블록을 출력하는 것만으로는 후크가 실행되지 않습니다.
- 등록된 Hook이 없거나 `.specify/extensions.yml`가 존재하지 않는 경우 자동으로 건너뜁니다.

## 개요

`.specify/memory/constitution.md`에서 프로젝트 구성을 업데이트하고 있습니다. 활성
구성 비계는 Spec Kit를 통해 `constitution-template`에서 명령 시간에 해결됩니다.
preset/template 해상도 스택.

다음 실행 흐름을 따르세요.

1. 리포지토리 루트에서 `.specify/scripts/powershell/resolve-template.ps1 constitution-template -Json`를 실행하고 `TEMPLATE_CONTENT`를 활성 템플릿으로 구문 분석합니다.
- 공유 리졸버는 프로젝트 재정의, 사전 설정 레이어 구성 및 확장 레이어를 적용합니다.
핵심 템플릿 대체 이전. 계속하려면 먼저 성공해야 합니다.
- 실패하면 중지하고 해결 오류를 보고합니다. 하나만 기여하는 것으로 계속하지 마십시오
템플릿 레이어.
- `.specify/memory/constitution.md`가 존재하는 경우 현재 프로젝트별 소스로 로드합니다.
가치와 수정. 새로 적용할 때 여전히 적용 가능한 정보를 보존합니다.
해결된 비계.
- 존재하지 않는 경우 해결된 템플릿을 초기 문서로 사용합니다.
- 버전이 지정된 템플릿 레이어에 다시 쓰지 마십시오.
- `[ALL_CAPS_IDENTIFIER]` 형식의 모든 자리 표시자 토큰을 식별합니다.
**중요**: 사용자는 템플릿에 사용된 원칙보다 더 적거나 더 많은 원칙을 요구할 수 있습니다. 숫자가 지정되면 이를 존중하고 일반 템플릿을 따르세요. 이에 따라 문서를 업데이트합니다.

2. 자리 표시자의 Collect/derive 값:
- 사용자 입력(대화)이 값을 제공하면 이를 사용합니다.
- 그렇지 않으면 기존 저장소 컨텍스트(README, 문서, 포함된 경우 이전 구성 버전)에서 추론합니다.
- 거버넌스 날짜의 경우: `RATIFICATION_DATE`는 원래 채택 날짜입니다(알 수 없는 경우 TODO를 묻거나 표시). 변경 사항이 있는 경우 `LAST_AMENDED_DATE`는 오늘이고, 그렇지 않은 경우 이전을 유지합니다.
- `CONSTITUTION_VERSION`는 의미론적 버전 관리 규칙에 따라 증가해야 합니다.
- 주요: 이전 버전과 호환되지 않는 governance/principle 제거 또는 재정의.
- 경미: 새로운 principle/section에 지침이 추가되거나 실질적으로 확장되었습니다.
- 패치: 설명, 표현, 오타 수정, 비의미적 개선.
- 버전 범프 유형이 모호한 경우 최종 결정 전에 추론을 제안합니다.

3. 해결된 템플릿을 필수 구조로 사용하여 업데이트된 헌법 콘텐츠 초안을 작성합니다.
- 모든 자리 표시자를 구체적인 텍스트로 바꿉니다(프로젝트에서 아직 정의하지 않기로 선택한 의도적으로 유지된 템플릿 슬롯을 제외하고 대괄호로 묶인 토큰은 남지 않습니다. 왼쪽을 명시적으로 정당화합니다).
- 제목 계층 구조를 유지하고 설명이 명확한 지침을 추가하지 않는 한 교체된 후 제거될 수 있습니다.
- 각 원칙 섹션을 보장합니다: 간결한 이름 줄, 협상할 수 없는 규칙을 포착하는 단락(또는 글머리 기호 목록), 명확하지 않은 경우 명시적인 근거.
- 거버넌스 섹션에 수정 절차, 버전 관리 정책 및 규정 준수 검토 기대 사항이 나열되어 있는지 확인합니다.

4. 동기화 영향 보고서를 생성합니다(업데이트 후 구성 파일 상단에 HTML 주석으로 추가).
- 버전 변경 : 기존 → 신규
- 수정된 원칙 목록(기존 제목 → 이름이 변경된 경우 새 제목)
- 섹션 추가
- 삭제된 섹션
- 자리 표시자가 의도적으로 연기된 경우 후속 TODO입니다.

5. 최종 출력 전 검증:
- 설명되지 않은 브래킷 토큰이 남아 있지 않습니다.
- 버전 라인이 보고서와 일치합니다.
- 날짜 ISO 형식 YYYY-MM-DD.
- 원칙은 선언적이고 테스트 가능하며 모호한 언어가 없습니다("should" → 적절한 경우 MUST/SHOULD 근거로 대체).

6. 완성된 구성을 `.specify/memory/constitution.md`에 다시 씁니다(덮어쓰기).

7. 다음을 사용하여 최종 요약을 사용자에게 출력합니다.
- 새 버전 및 범프 이론적 근거.
- 수동 후속 조치가 필요한 모든 TODO 자리 표시자 또는 지연된 항목.
- 제안된 커밋 메시지(예: `docs: amend constitution to vX.Y.Z (principle additions + governance update)`).
- 연기된 비거버넌스 의도에 대한 `Next Actions` 섹션.

형식 및 스타일 요구 사항:

- 마크다운 제목을 템플릿과 동일하게 사용하세요(demote/promote 수준은 사용하지 마세요).
- 가독성을 유지하기 위해 긴 근거 줄을 감싸되(이상적으로는 100자 미만) 어색한 줄바꿈을 강제로 적용하지 마세요.
- 섹션 사이에 빈 줄을 하나 두십시오.
- 후행 공백을 피하세요.

사용자가 부분 업데이트(예: 하나의 원칙 개정만)를 제공하는 경우에도 유효성 검사 및 버전 결정 단계를 수행합니다.

중요한 정보가 누락된 경우(예: 비준 날짜를 실제로 알 수 없음) `TODO(<FIELD_NAME>): explanation`를 삽입하고 연기된 항목 아래의 동기화 영향 보고서에 포함합니다.

`.specify/memory/constitution.md`만 쓰십시오. 템플릿 소스 파일을 생성하거나 수정하지 마십시오.
