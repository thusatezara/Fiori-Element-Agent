## 체크리스트 목적: "영어 단위 테스트"

**중요 개념**: 체크리스트는 **요구사항 작성을 위한 단위 테스트**입니다. 이는 특정 도메인에서 요구사항의 품질, 명확성 및 완전성을 검증합니다.

**verification/testing**에는 해당되지 않음:

- ❌ "버튼이 올바르게 클릭되는지 확인"이 아닙니다.
- ❌ "테스트 오류 처리가 작동합니다"가 아닙니다.
- ❌ "API가 200을 반환하는지 확인하세요."
- ❌ code/implementation가 사양과 일치하는지 확인하지 않음

**요구사항 품질 검증의 경우**:

- ✅ "모든 카드 유형에 대해 시각적 계층 구조 요구 사항이 정의되어 있습니까?" (완전성)
- ✅ "'눈에 띄는 디스플레이'는 특정 sizing/positioning로 수량화되나요?" (명확함)
- ✅ "호버 상태 요구 사항은 모든 대화형 요소에서 일관됩니까?" (일관성)
- ✅ "키보드 탐색에 대한 접근성 요구 사항이 정의되어 있나요?" (취재)
- ✅ "로고 이미지가 로드되지 않을 때 발생하는 일이 사양에 정의되어 있나요?" (극단적인 경우)

**은유**: 사양이 영어로 작성된 코드인 경우 체크리스트는 단위 테스트 모음입니다. 요구 사항이 잘 작성되고, 완전하고, 명확하고, 구현 준비가 되었는지 테스트하는 것이지 구현이 제대로 작동하는지 여부가 아닙니다.

**소유권 및 체크박스 수명 주기**:

- 이 명령으로 생성된 사용자 정의 체크리스트는 검토자가 소유한 요구 사항 품질 검토 아티팩트입니다.
- `[x]`는 검토자가 요구사항 품질 기준이 충족되었다고 결정했음을 의미합니다.
- `[x]`는 구현 작업이 완료되었음을 의미하지 않습니다.
- 이 명령은 체크리스트 항목을 생성하거나 추가합니다. 생성된 항목 `[x]`를 표시해서는 안 됩니다.
- 에이전트는 리뷰어가 명시적으로 요청한 경우에만 항목 평가를 지원할 수 있습니다.
- `checklists/requirements.md`는 `$speckit-specify` 및 `$speckit-clarify`에서 관리하는 별도의 내장 사양 품질 체크리스트입니다. 여기에서 생성된 사용자 정의 체크리스트에 적용되는 것으로 해당 예외를 처리하지 마십시오.

## 사용자 입력

```text
$ARGUMENTS
```

진행하기 전에 **반드시** 사용자 입력을 고려해야 합니다(비어 있지 않은 경우).

## 실행 전 검사

**확장 후크 확인(체크리스트 생성 전)**:
- 프로젝트 루트에 `.specify/extensions.yml`가 존재하는지 확인하세요.
- 존재하는 경우 이를 읽고 `hooks.before_checklist` 키 아래 항목을 찾습니다.
- YAML을 파싱할 수 없거나 유효하지 않은 경우 후크 검사를 자동으로 건너뛰고 정상적으로 계속 진행합니다.
- `enabled`가 명시적으로 `false`인 후크를 필터링합니다. `enabled` 필드가 없는 후크는 기본적으로 활성화된 것으로 처리합니다.
- 나머지 각 후크에 대해 후크 `condition` 표현식을 해석하거나 평가하려고 **하지 마세요**.
- 후크에 `condition` 필드가 없거나 null/empty인 경우 후크를 실행 가능한 것으로 처리합니다.
- 후크가 비어 있지 않은 `condition`를 정의하는 경우 후크를 건너뛰고 조건 평가를 HookExecutor 구현에 맡깁니다.
- 후크 명령 이름으로 명령 호출을 구성할 때 점(`.`)을 하이픈(`-`)으로 바꾸십시오. 예를 들어 `speckit.git.commit` → `$speckit-git-commit`입니다.
- 각 실행 가능한 후크에 대해 `optional` 플래그를 기반으로 다음을 출력합니다.
- **후크 옵션**(`optional: true`):
    ```
## 확장 후크

**옵션 프리훅**: {extension}
명령: `/{command}`
설명: {description}

프롬프트: {prompt}
실행하려면: `/{command}`
    ```
- **필수 후크** (`optional: false`):
    ```
## 확장 후크

**자동 프리훅**: {extension}
실행 중: `/{command}`
EXECUTE_COMMAND: {command}

실행 단계를 진행하기 전에 후크 명령의 결과를 기다리십시오.
    ```
위의 블록을 출력한 후에는 실제로 후크를 호출하고 계속하기 전에 완료될 때까지 기다려야 합니다. 이 에이전트/세션에서 직접 명령을 실행하는 것과 동일한 방식으로 실행합니다(호출은 위에 표시된 리터럴 `{command}` ID와 다를 수 있습니다. 예를 들어 기술 모드 에이전트는 이를 `/skill:speckit-...` 또는 `$speckit-...`로 실행합니다). 블록을 출력하는 것만으로는 후크가 실행되지 않습니다.
- 등록된 Hook이 없거나 `.specify/extensions.yml`가 존재하지 않는 경우 자동으로 건너뜁니다.

## 실행 단계

1. **설정**: 저장소 루트에서 `.specify/scripts/powershell/check-prerequisites.ps1 -Json -Template checklist-template`를 실행하고 FEATURE_DIR, AVAILABLE_DOCS 목록 및 TEMPLATE_CONTENT에 대해 JSON을 구문 분석합니다.
- 모든 파일 경로는 절대 경로여야 합니다.
- "I'm Groot"와 같이 인수에 작은따옴표를 사용하려면 이스케이프 구문을 사용하세요. 예: 'I'\''m Groot'(또는 가능하면 큰따옴표: "I'm Groot").

2. **존재하는 경우**: 프로젝트 원칙 및 거버넌스 제약 조건에 대해 `.specify/memory/constitution.md`를 로드합니다.

3. **의도 명확화(동적)**: 최대 3개의 초기 상황별 명확화 질문을 도출합니다(사전 구운 카탈로그 없음). 그들은 반드시:
- 사용자의 문구에서 생성 + spec/plan/tasks에서 추출된 신호
- 체크리스트 내용을 실질적으로 변경하는 정보에 대해서만 문의하세요.
- `$ARGUMENTS`에서 이미 명확한 경우 개별적으로 건너뜁니다.
- 폭보다 정밀도를 선호합니다.

생성 알고리즘:
1. 신호 추출: 기능 도메인 키워드(예: 인증, 대기 시간, UX, API), 위험 지표("중요", "필수", "규정 준수"), 이해 관계자 힌트("QA", "검토", "보안 팀") 및 명시적인 결과물("a11y", "롤백", "계약").
2. 관련성에 따라 순위가 매겨진 후보 초점 영역(최대 4개)으로 신호를 클러스터링합니다.
3. 명시적이지 않은 경우 예상 독자 및 시기(저자, 검토자, QA, 릴리스)를 식별합니다.
4. 누락된 차원을 감지합니다: 범위 폭, depth/rigor, 위험 강조, 제외 경계, 측정 가능한 허용 기준.
5. 다음 원형에서 선택한 질문을 공식화하십시오.
- 범위 개선(예: "X 및 Y와의 통합 터치포인트를 포함해야 합니까, 아니면 로컬 모듈 정확성으로 제한해야 합니까?")
- 위험 우선 순위 지정(예: "이러한 잠재적 위험 영역 중 필수 게이팅 확인을 받아야 하는 영역은 무엇입니까?")
- 깊이 교정(예: "이것은 가벼운 사전 커밋 온전성 목록입니까, 아니면 공식 릴리스 게이트입니까?")
- 청중 프레이밍(예: "PR 검토 중에 저자만 사용할 것인가 아니면 동료가 사용할 것인가?")
- 경계 제외(예: "이번 라운드에서 성능 튜닝 항목을 명시적으로 제외해야 할까요?")
- 시나리오 클래스 차이(예: "복구 흐름이 감지되지 않음 - 롤백/부분 실패 경로가 범위 내에 있습니까?")

질문 형식 규칙:
- 옵션을 제시하는 경우 열이 포함된 간단한 테이블을 생성합니다. 옵션 | 후보 | 중요한 이유
- A~E 옵션은 최대로 제한됩니다. 자유 형식 답변이 더 명확하면 표를 생략하세요.
- 사용자에게 이미 말한 내용을 다시 말하도록 요청하지 마세요.
- 추측적인 범주를 피하십시오(환각 없음). 확실하지 않은 경우 명시적으로 질문하세요. "X가 범위에 속하는지 확인하세요."

상호 작용이 불가능할 때의 기본값:
- 깊이 : 표준
- 대상: 코드 관련인 경우 검토자(PR); 그렇지 않은 경우 작성자
- 초점: 상위 2개 관련성 클러스터

질문을 출력합니다(레이블 Q1/Q2/Q3). 답변 후: 2개 이상의 시나리오 클래스(대체/예외/복구/비기능 도메인)가 불분명한 경우 각 한 줄 근거(예: "해결되지 않은 복구 경로 위험")를 사용하여 최대 2개의 추가 대상 후속 조치(Q4/Q5)를 요청할 수 있습니다. 총 질문 수는 5개를 초과하지 마십시오. 사용자가 명시적으로 더 이상 거부하는 경우 에스컬레이션을 건너뜁니다.

4. **사용자 요청 이해**: `$ARGUMENTS` + 명확한 답변을 결합합니다.
- 체크리스트 테마 도출(예: 보안, 검토, 배포, UX)
- 사용자가 언급한 명시적인 필수 항목을 통합합니다.
- 카테고리 비계에 초점 선택 매핑
- spec/plan/tasks에서 누락된 컨텍스트를 추론합니다(환각하지 마세요).

5. **기능 컨텍스트 로드**: FEATURE_DIR에서 읽습니다.
- spec.md: 기능 요구 사항 및 범위
- plan.md(존재하는 경우): 기술 세부정보, 종속성
- tasks.md(존재하는 경우): 구현 작업

**컨텍스트 로딩 전략**:
- 활성 초점 영역과 관련된 필요한 부분만 로드(전체 파일 덤핑 방지)
- 긴 섹션을 간결한 scenario/requirement 글머리 기호로 요약하는 것을 선호합니다.
- 점진적 공개 사용: 공백이 발견된 경우에만 후속 검색을 추가합니다.
- 소스 문서가 큰 경우 원시 텍스트를 포함하는 대신 중간 요약 항목을 생성합니다.

6. **체크리스트 생성** - TEMPLATE_CONTENT를 구조 템플릿으로 사용하고 "요구 사항에 대한 단위 테스트"를 만듭니다.
- `FEATURE_DIR/checklists/` 디렉토리가 존재하지 않는 경우 생성합니다.
- 고유한 체크리스트 파일 이름 생성:
- 도메인을 기반으로 짧고 설명이 포함된 이름을 사용합니다(예: `ux.md`, `api.md`, `security.md`).
- 형식: `[domain].md`
- 파일 처리 동작:
- 파일이 존재하지 않는 경우: CHK001부터 시작하여 새로운 파일 및 번호 항목을 생성합니다.
- 파일이 존재하는 경우: 기존 파일에 새 항목을 추가하고 마지막 CHK ID부터 계속합니다. (예: 마지막 항목이 CHK015인 경우 CHK016에서 새 항목을 시작합니다.)
- 기존 체크리스트 내용을 절대 삭제하거나 교체하지 마세요. 항상 보존하고 추가하세요.
- 새로 생성된 모든 항목을 선택하지 않은 상태로 둡니다(`[ ]`). 확인란 상태는 검토자에게 속합니다.

**핵심 원칙 - 구현이 아닌 요구 사항을 테스트**:
모든 체크리스트 항목은 다음에 대한 요구 사항을 평가해야 합니다.
- **완전성**: 필요한 요구사항이 모두 존재합니까?
- **명확성**: 요구 사항이 명확하고 구체적입니까?
- **일관성**: 요구사항이 서로 일치합니까?
- **측정 가능성**: 요구사항을 객관적으로 검증할 수 있습니까?
- **적용 범위**: 모든 scenarios/edge 사례가 해결됩니까?

**카테고리 구조** - 요구 사항 품질 차원별로 항목을 그룹화합니다.
- **요구사항 완전성**(필요한 모든 요구사항이 문서화되어 있습니까?)
- **요구사항 명확성**(요구사항이 구체적이고 명확합니까?)
- **요구사항 일관성**(요구사항이 충돌 없이 정렬됩니까?)
- **수락 기준 품질**(성공 기준을 측정할 수 있습니까?)
- **시나리오 적용 범위**(flows/cases가 모두 해결되었나요?)
- **Edge Case Coverage** (경계 조건이 정의되어 있습니까?)
- **비기능적 요구사항**(성능, 보안, 접근성 등 - 지정되어 있습니까?)
- **종속성 및 가정**(문서화되고 검증되었습니까?)
- **모호함 및 갈등** (설명이 필요한 부분은 무엇입니까?)

**체크리스트 항목 작성 방법 - "영어 단위 테스트"**:

❌ **잘못됨** (테스트 구현):
- "랜딩 페이지에 3개의 에피소드 카드가 표시되는지 확인하세요."
- "테스트 호버 상태는 데스크톱에서 작동합니다."
- "로고 확인을 클릭하면 홈으로 이동합니다."

✅ **올바른** (테스트 요구 사항 품질):
- "특집 에피소드의 정확한 수와 레이아웃이 명시되어 있습니까?" [완전성]
- "'눈에 띄는 디스플레이'는 특정 sizing/positioning로 수량화됩니까?" [선명도]
- "호버 상태 요구 사항은 모든 대화형 요소에서 일관됩니까?" [일관성]
- "모든 대화형 UI에 대해 키보드 탐색 요구 사항이 정의되어 있습니까?" [취재범위]
- "로고 이미지 로드에 실패할 경우 대체 동작이 지정되어 있습니까?" [엣지 케이스]
- "비동기 에피소드 데이터에 대한 로드 상태가 정의되어 있습니까?" [완전성]
- "사양은 경쟁 UI 요소에 대한 시각적 계층 구조를 정의합니까?" [선명도]

**아이템 구조**:
각 항목은 다음 패턴을 따라야 합니다.
- 요구사항 품질을 묻는 질문 형식
- spec/plan에 WRITTEN(또는 기록되지 않은) 내용에 중점을 둡니다.
- 괄호 안에 품질 치수 포함 [Completeness/Clarity/Consistency/etc.]
- 기존 요구 사항 확인 시 스펙 섹션 `[Spec §X.Y]` 참조
- 누락된 요구사항을 확인할 때 `[Gap]` 마커를 사용하세요.

**품질 차원별 예**:

   Completeness:
- "모든 API 실패 모드에 대해 오류 처리 요구 사항이 정의되어 있습니까? [간격]"
- "모든 대화형 요소에 대한 접근성 요구 사항이 지정되어 있습니까? [완전성]"
- "반응형 레이아웃에 대해 모바일 중단점 요구 사항이 정의되어 있습니까? [간격]"

   Clarity:
- "'빠른 로딩'은 특정 타이밍 임계값으로 정량화됩니까? [Clarity, Spec §NFR-2]"
- "'관련 에피소드' 선택 기준이 명시적으로 정의되어 있나요? [Clarity, Spec §FR-5]"
- "'탁월함'은 측정 가능한 시각적 특성으로 정의됩니까? [모호함, 사양 §FR-4]"

   Consistency:
- "탐색 요구 사항이 모든 페이지에서 일치합니까? [일관성, 사양 §FR-10]"
- "랜딩 페이지와 세부 정보 페이지 간의 카드 구성 요소 요구 사항이 일관됩니까? [일관성]"

   Coverage:
- "제로 상태 시나리오(에피소드 없음)에 대한 요구 사항이 정의되어 있습니까? [범위, 엣지 케이스]"
- "동시 사용자 상호 작용 시나리오가 해결되었습니까? [범위, 격차]"
- "부분 데이터 로딩 실패에 대한 요구 사항이 지정되어 있습니까? [적용 범위, 예외 흐름]"

   Measurability:
- "시각적 계층 구조 요구 사항은 measurable/testable입니까? [수용 기준, 사양 §FR-1]"
- "'균형 잡힌 시각적 무게'를 객관적으로 검증할 수 있는가? [측정성, 스펙 §FR-2]"

**시나리오 분류 및 적용 범위**(요구 사항 품질 중심):
- 기본, 대체, Exception/Error, 복구, 비기능 시나리오에 대한 요구 사항이 있는지 확인하십시오.
- 각 시나리오 클래스에 대해 "[시나리오 유형] 요구 사항이 완전하고 명확하며 일관성이 있습니까?"라고 질문합니다.
- 시나리오 클래스가 누락된 경우: "[시나리오 유형] 요구 사항이 의도적으로 제외되었거나 누락되었습니까? [간격]"
- 상태 변형이 발생할 때 resilience/rollback를 포함합니다. "마이그레이션 실패에 대한 롤백 요구 사항이 정의되어 있습니까? [간격]"

**추적성 요구 사항**:
- 최소: 품목의 ≥80%에는 최소한 하나의 추적성 참조가 포함되어야 합니다.
- 각 항목은 다음을 참조해야 합니다: 사양 섹션 `[Spec §X.Y]` 또는 마커 사용: `[Gap]`, `[Ambiguity]`, `[Conflict]`, `[Assumption]`
- ID 시스템이 존재하지 않는 경우: "요구사항 및 승인 기준 ID 체계가 확립되어 있습니까? [추적성]"

**문제 표면화 및 해결**(요구사항 품질 문제):
요구 사항 자체에 대해 질문하십시오.
- 모호함: "'빠른'이라는 용어가 특정 지표로 수량화되었습니까? [모호함, 사양 §NFR-1]"
- 충돌: "§FR-10과 §FR-10a 사이의 탐색 요구 사항이 충돌합니까? [충돌]"
- 가정: "'항상 사용 가능한 팟캐스트 API'라는 가정이 유효합니까? [가정]"
- 종속성: "외부 팟캐스트 API 요구 사항이 문서화되어 있습니까? [종속성, 격차]"
- 정의 누락: "'시각적 계층 구조'가 측정 가능한 기준으로 정의되어 있습니까? [간격]"

**컨텐츠 통합**:
- 소프트 캡: 원시 후보 항목 > 40인 경우 risk/impact로 우선 순위 지정
- 동일한 요구 사항 측면을 확인하면서 거의 중복된 항목을 병합합니다.
- 영향이 적은 엣지 케이스가 5개를 초과하는 경우 다음 항목 하나를 만듭니다. "최종 케이스 X, Y, Z가 요구 사항에서 처리됩니까? [적용 범위]"

**🚫 절대 금지** - 요구 사항 테스트가 아닌 구현 테스트가 됩니다.
- ❌ "Verify", "Test", "Confirm", "Check"로 시작하는 모든 항목 + 구현 동작
- ❌ 코드 실행, 사용자 동작, 시스템 동작에 대한 참조
- ❌ "올바르게 표시됩니다", "제대로 작동합니다", "예상대로 작동합니다"
- ❌ "클릭", "탐색", "렌더링", "로드", "실행"
- ❌ 테스트 케이스, 테스트 계획, QA 절차
- ❌ 구현 세부정보(프레임워크, API, 알고리즘)

**✅ 필수 패턴** - 테스트 요구 사항 품질:
- ✅ "[시나리오]의 [요구사항 유형]이 defined/specified/documented인가요?"
- ✅ "[모호한 용어] quantified/clarified는 구체적인 기준이 있나요?"
- ✅ "[섹션 A]와 [섹션 B] 간의 요구 사항이 일치합니까?"
- ✅ "[요구사항]이 객관적으로 measured/verified일 수 있나요?"
- ✅ "요구사항에서 [edge cases/scenarios]가 해결되었나요?"
- ✅ "스펙이 [누락된 측면]을 정의합니까?"

7. **구조 참조**: 제목, 메타 섹션, 카테고리 제목, 소유권 메모, 메모 섹션 및 ID 형식에 대한 `.specify/templates/checklist-template.md`의 표준 템플릿에 따라 체크리스트를 생성합니다. 템플릿을 사용할 수 없는 경우 다음을 사용하십시오: H1 제목, purpose/created 메타 라인, `[x]`가 요구 사항 품질에 대한 검토자의 승인을 의미함을 설명하는 소유권 메모, CHK001에서 시작하여 전역적으로 증가하는 ID가 있는 `- [ ] CHK### <requirement item>` 라인을 포함하는 `##` 카테고리 섹션, 그리고 `$speckit-implement`가 체크리스트 상태를 읽지만 수정하지는 않는다는 메모를 사용합니다. 마커.

8. **보고서**: 체크리스트 파일의 전체 경로, 항목 수를 출력하고 실행이 새 파일을 생성했는지 또는 기존 파일에 추가했는지 요약합니다. 요약:
- 중점 분야 선택
- 깊이 수준
- Actor/timing
- 명시적으로 사용자가 지정한 필수 항목이 포함되어 있습니다.

**중요**: 각 `$speckit-checklist` 명령 호출은 짧고 설명이 포함된 체크리스트 파일 이름을 사용하며 새 파일을 생성하거나 기존 파일에 추가합니다. 이를 통해 다음이 가능합니다.

- 다양한 유형의 여러 체크리스트(예: `ux.md`, `test.md`, `security.md`)
- 체크리스트 목적을 나타내는 간단하고 기억에 남는 파일 이름
- `checklists/` 폴더에서 쉽게 식별하고 탐색할 수 있습니다.

혼란을 피하려면 설명적인 유형을 사용하고 완료되면 사용되지 않는 체크리스트를 정리하십시오.

## 반대 예: 하지 말아야 할 것

**❌ 틀렸음 - 요구사항이 아닌 테스트 구현:**

```markdown
- [ ] CHK001 - 방문 페이지에 3개의 에피소드 카드가 표시되는지 확인합니다. [Spec §FR-001]
- [ ] CHK002 - 테스트 호버 상태가 데스크탑에서 올바르게 작동합니다. [Spec §FR-003]
- [ ] CHK003 - 로고 확인을 클릭하면 홈 페이지로 이동합니다. [Spec §FR-010]
- [ ] CHK004 - 관련 에피소드 섹션에 3~5개 항목이 표시되는지 확인 [Spec §FR-005]
```

**✅ 정확함 - 테스트 요구 사항 품질:**

```markdown
- [ ] CHK001 - 특집 에피소드의 수와 레이아웃이 명시적으로 지정되어 있습니까? [완전성, Spec §FR-001]
- [ ] CHK002 - 모든 대화형 요소에 대해 호버 상태 요구 사항이 일관되게 정의되어 있습니까? [일관성, Spec §FR-003]
- [ ] CHK003 - 클릭 가능한 모든 브랜드 요소에 대한 탐색 요구 사항이 명확합니까? [선명도, 사양 §FR-010]
- [ ] CHK004 - 관련 에피소드의 선정 기준이 문서화되어 있습니까? [갭, 스펙 §FR-005]
- [ ] CHK005 - 비동기 에피소드 데이터에 대해 로드 상태 요구 사항이 정의되어 있습니까? [갭]
- [ ] CHK006 - "시각적 계층 구조" 요구 사항을 객관적으로 측정할 수 있습니까? [측정성, Spec §FR-001]
```

**주요 차이점:**

- 틀렸음: 시스템이 올바르게 작동하는지 테스트합니다.
- Correct: 요구사항이 올바르게 작성되었는지 테스트합니다.
- 틀림: 행동 검증
- 정확함: 요구사항 품질 검증
- 틀렸음: "X를 수행합니까?"
- 정확함: "X가 명확하게 지정되어 있습니까?"

## 실행 후 확인

**확장 후크 확인(체크리스트 생성 후)**:
프로젝트 루트에 `.specify/extensions.yml`가 있는지 확인하세요.
- 존재하는 경우 이를 읽고 `hooks.after_checklist` 키 아래 항목을 찾습니다.
- YAML을 파싱할 수 없거나 유효하지 않은 경우 후크 검사를 자동으로 건너뛰고 정상적으로 계속 진행합니다.
- `enabled`가 명시적으로 `false`인 후크를 필터링합니다. `enabled` 필드가 없는 후크는 기본적으로 활성화된 것으로 처리합니다.
- 나머지 각 후크에 대해 후크 `condition` 표현식을 해석하거나 평가하려고 **하지 마세요**.
- 후크에 `condition` 필드가 없거나 null/empty인 경우 후크를 실행 가능한 것으로 처리합니다.
- 후크가 비어 있지 않은 `condition`를 정의하는 경우 후크를 건너뛰고 조건 평가를 HookExecutor 구현에 맡깁니다.
- 후크 명령 이름으로 명령 호출을 구성할 때 점(`.`)을 하이픈(`-`)으로 바꾸십시오. 예를 들어 `speckit.git.commit` → `$speckit-git-commit`입니다.
- 각 실행 가능한 후크에 대해 `optional` 플래그를 기반으로 다음을 출력합니다.
- **후크 옵션**(`optional: true`):

위의 블록을 출력한 후에는 실제로 후크를 호출하고 계속하기 전에 완료될 때까지 기다려야 합니다. 이 에이전트/세션에서 직접 명령을 실행하는 것과 동일한 방식으로 실행합니다(호출은 위에 표시된 리터럴 `{command}` ID와 다를 수 있습니다. 예를 들어 기술 모드 에이전트는 이를 `/skill:speckit-...` 또는 `$speckit-...`로 실행합니다). 블록을 출력하는 것만으로는 후크가 실행되지 않습니다.
- 등록된 Hook이 없거나 `.specify/extensions.yml`가 존재하지 않는 경우 자동으로 건너뜁니다.
