## 사용자 입력

```text
$ARGUMENTS
```

진행하기 전에 **반드시** 사용자 입력을 고려해야 합니다(비어 있지 않은 경우).

## 실행 전 검사

**연장 후크 확인(사양 전)**:
- 프로젝트 루트에 `.specify/extensions.yml`가 존재하는지 확인하세요.
- 존재하는 경우 이를 읽고 `hooks.before_specify` 키 아래 항목을 찾습니다.
- YAML을 파싱할 수 없거나 유효하지 않은 경우 후크 검사를 자동으로 건너뛰고 정상적으로 계속 진행합니다.
- `enabled`가 명시적으로 `false`인 후크를 필터링합니다. `enabled` 필드가 없는 후크는 기본적으로 활성화된 것으로 처리합니다.
- 나머지 각 후크에 대해 후크 `condition` 표현식을 해석하거나 평가하려고 **하지 마세요**.
- 후크에 `condition` 필드가 없거나 null/empty인 경우 후크를 실행 가능한 것으로 처리합니다.
- 후크가 비어 있지 않은 `condition`를 정의하는 경우 후크를 건너뛰고 조건 평가를 HookExecutor 구현에 맡깁니다.
- 후크 명령 이름으로 명령 호출을 구성할 때 점(`.`)을 하이픈(`-`)으로 바꾸십시오. 예를 들어 `speckit.git.commit` → `$speckit-git-commit`입니다.
- 각 실행 가능한 후크에 대해 `optional` 플래그를 기반으로 다음을 출력합니다.
- **후크 옵션**(`optional: true`):
    ```
## 확장 후크

**옵션 프리훅**: {extension}
명령: `/{command}`
설명: {description}

프롬프트: {prompt}
실행하려면: `/{command}`
    ```
- **필수 후크** (`optional: false`):
    ```
## 확장 후크

**자동 프리훅**: {extension}
실행 중: `/{command}`
EXECUTE_COMMAND: {command}

개요로 진행하기 전에 후크 명령의 결과를 기다리십시오.
    ```
위의 블록을 출력한 후에는 실제로 후크를 호출하고 계속하기 전에 완료될 때까지 기다려야 합니다. 이 에이전트/세션에서 직접 명령을 실행하는 것과 동일한 방식으로 실행합니다(호출은 위에 표시된 리터럴 `{command}` ID와 다를 수 있습니다. 예를 들어 기술 모드 에이전트는 이를 `/skill:speckit-...` 또는 `$speckit-...`로 실행합니다). 블록을 출력하는 것만으로는 후크가 실행되지 않습니다.
- 등록된 Hook이 없거나 `.specify/extensions.yml`가 존재하지 않는 경우 자동으로 건너뜁니다.

## 개요

트리거 메시지에서 `$speckit-specify` 뒤에 사용자가 입력한 텍스트는 기능 설명입니다. `$ARGUMENTS`가 문자 그대로 아래에 나타나더라도 이 대화에서 항상 사용할 수 있다고 가정합니다. 빈 명령을 제공하지 않는 한 사용자에게 반복하도록 요청하지 마십시오.

해당 기능 설명이 주어지면 다음을 수행하십시오.

1. 기능에 대한 **간결한 짧은 이름**(2~4단어)을 생성합니다.
- 기능 설명을 분석하여 가장 의미 있는 키워드 추출
- 기능의 본질을 포착하는 2~4단어의 짧은 이름을 만듭니다.
- 가능하면 액션-명사 형식을 사용하세요(예: '사용자 인증 추가', '결제 버그 수정').
- 기술 용어 및 약어(OAuth2, API, JWT 등)를 유지합니다.
- 간결하게 작성하되 한눈에 기능을 이해할 수 있을 만큼 설명적이어야 합니다.
   - Examples:
- "사용자 인증을 추가하고 싶어요" → "user-auth"
- "API에 대한 OAuth2 통합 구현" → "oauth2-api-integration"
- "분석용 대시보드 만들기" → "analytics-dashboard"
- "결제 처리 시간 초과 버그 수정" → "결제 시간 초과 수정"

2. **브랜치 생성**(선택 사항, 후크를 통해):

위의 사전 실행 확인에서 `before_specify` 후크가 성공적으로 실행된 경우 git 브랜치에 created/switched가 있고 `BRANCH_NAME` 및 `FEATURE_NUM`가 포함된 JSON가 출력됩니다. 참조용으로 이 값을 기록해 두세요. 하지만 브랜치 이름이 사양 디렉터리 이름을 나타내지는 **않습니다**.

사용자가 `GIT_BRANCH_NAME`를 명시적으로 제공한 경우 이를 후크에 전달하여 분기 스크립트가 정확한 값을 분기 이름으로 사용하도록 합니다(모든 prefix/suffix 생성을 우회).

3. **사양 기능 디렉터리 생성**:

사양은 사용자가 명시적으로 `SPECIFY_FEATURE_DIRECTORY`를 제공하지 않는 한 기본 `specs/` 디렉터리에 있습니다.

**`SPECIFY_FEATURE_DIRECTORY`의 해결 순서**:
1. 사용자가 `SPECIFY_FEATURE_DIRECTORY`를 명시적으로 제공한 경우(예: 환경 변수, 인수 또는 구성을 통해) 그대로 사용합니다.
2. 그렇지 않으면 `specs/`에서 자동 생성합니다.
- `feature_numbering`(선호) 또는 `branch_numbering`(더 이상 사용되지 않음, 마이그레이션만 해당 - 향후 릴리스에서 제거됨)에 대해서는 `.specify/init-options.json`를 확인하세요.
- `"timestamp"`인 경우: 접두사는 `YYYYMMDD-HHMMSS`(현재 타임스탬프)입니다.
- `"sequential"` 또는 없는 경우: 접두사는 `NNN`입니다(`specs/`에서 기존 디렉터리를 스캔한 후 다음으로 사용 가능한 3자리 숫자).
- 디렉토리 이름 구성: `<prefix>-<short-name>`(예: `003-user-auth` 또는 `20260319-143022-user-auth`)
- `SPECIFY_FEATURE_DIRECTORY`를 `specs/<directory-name>`로 설정
- `branch_numbering`가 사용된 경우(그리고 `feature_numbering`가 없는 경우) 다음 한 줄 경고를 표시합니다. "⚠️ init-options.json의 `branch_numbering`는 더 이상 사용되지 않습니다. 이름을 `feature_numbering`로 변경하세요."

**디렉토리 및 사양 파일 만들기**:
- `mkdir -p SPECIFY_FEATURE_DIRECTORY`
- Spec Kit preset/template 분해능 스택(`specify preset resolve spec-template`와 동일)을 통해 활성 `spec-template`를 분해합니다.
- 해결된 `spec-template` 파일을 시작점으로 `SPECIFY_FEATURE_DIRECTORY/spec.md`에 복사합니다.
- `SPEC_FILE`를 `SPECIFY_FEATURE_DIRECTORY/spec.md`로 설정
- `.specify/feature.json`에 대한 확인된 경로를 유지합니다.
     ```json
     {
       "feature_directory": "<resolved feature dir>"
     }
     ```
리터럴 문자열 `SPECIFY_FEATURE_DIRECTORY`가 아닌 실제 확인된 디렉터리 경로 값(예: `specs/003-user-auth`)을 작성합니다.
이를 통해 다운스트림 명령(`$speckit-plan`, `$speckit-tasks` 등)이 git 분기 이름 규칙에 의존하지 않고 기능 디렉터리를 찾을 수 있습니다.

**중요**:
- `$speckit-specify` 호출당 하나의 기능만 생성해야 합니다.
- 스펙 디렉토리 이름과 git 브랜치 이름은 독립적입니다. 동일할 수도 있지만 이는 사용자가 선택합니다.
- 사양 디렉터리와 파일은 후크에 의해 생성되지 않고 항상 이 명령에 의해 생성됩니다.

4. 해결된 활성 `spec-template` 파일을 로드하여 필수 섹션을 이해합니다.

5. **존재하는 경우**: 프로젝트 원칙 및 거버넌스 제약 조건에 대해 `.specify/memory/constitution.md`를 로드합니다.

6. 다음 실행 흐름을 따르십시오.
1. 인수에서 사용자 설명을 구문 분석합니다.
비어 있는 경우: 오류 "기능 설명이 제공되지 않았습니다."
2. 설명에서 핵심 개념 추출
식별: 행위자, 작업, 데이터, 제약 조건
3. 불분명한 측면의 경우:
- 상황과 업계 표준을 기반으로 정보에 입각한 추측을 해보세요.
- 다음과 같은 경우에만 [설명 필요: 특정 질문]으로 표시하세요.
- 선택은 기능 범위나 사용자 경험에 큰 영향을 미칩니다.
- 다양한 의미를 지닌 다양한 합리적인 해석이 존재함
- 합리적인 기본값이 존재하지 않습니다.
- **한도: 총 최대 3개의 [NEEDS CLARIFICATION] 마커**
- 영향에 따라 설명의 우선순위 지정: 범위 > security/privacy > 사용자 경험 > 기술 세부정보
4. 사용자 시나리오 및 테스트 섹션 작성
명확한 사용자 흐름이 없는 경우: 오류 "사용자 시나리오를 결정할 수 없습니다"
5. 기능적 요구사항 생성
각 요구사항은 테스트 가능해야 합니다.
지정되지 않은 세부 사항에 대해서는 합리적인 기본값을 사용합니다(가정 섹션에 가정을 문서화함).
6. 성공 기준 정의
측정 가능하고 기술에 구애받지 않는 결과 생성
정량적 지표(시간, 성과, 양)와 정성적 지표(사용자 만족도, 작업 완료)를 모두 포함합니다.
각 기준은 구현 세부정보 없이 검증 가능해야 합니다.
7. 주요 엔터티 식별(데이터가 관련된 경우)
8. 반환: SUCCESS(계획 준비가 완료된 사양)

7. 섹션 순서와 제목을 유지하면서 자리 표시자를 기능 설명(인수)에서 파생된 구체적인 세부 정보로 대체하여 템플릿 구조를 사용하여 SPEC_FILE에 사양을 작성합니다.

8. **사양 품질 검증**: 초기 사양을 작성한 후 품질 기준에 따라 검증합니다.

가. **사양 품질 체크리스트 생성**: 다음 검증 항목이 포함된 체크리스트 템플릿 구조를 사용하여 `SPECIFY_FEATURE_DIRECTORY/checklists/requirements.md`에서 체크리스트 파일을 생성합니다.

      ```markdown
# 사양 품질 체크리스트: [기능 이름]

**목적**: 계획을 진행하기 전에 사양 완전성과 품질을 검증합니다.
**생성됨**: [날짜]
**특징**: [spec.md 링크]

## 콘텐츠 품질

- [ ] 구현 세부 정보 없음(언어, 프레임워크, API)
- [ ] 사용자 가치와 비즈니스 요구에 중점을 둡니다.
- [ ] 비기술적 이해관계자를 위해 작성됨
- [ ] 필수 항목 모두 작성 완료

## 요구사항 완전성

- [ ] [NEEDS CLARIFICATION] 마커가 남아 있지 않습니다.
- [ ] 요구사항이 테스트 가능하고 명확합니다.
- [ ] 성공 기준을 측정할 수 있습니다.
- [ ] 성공 기준은 기술에 구애받지 않습니다(구현 세부 사항 없음).
- [ ] 모든 승인 시나리오가 정의되었습니다.
- [ ] 엣지 케이스가 식별됨
- [ ] 범위가 명확하게 제한되어 있습니다.
- [ ] 식별된 종속성 및 가정

## 기능 준비

- [ ] 모든 기능 요구사항에는 명확한 승인 기준이 있습니다.
- [ ] 사용자 시나리오는 기본 흐름을 다룹니다.
- [ ] 기능이 성공 기준에 정의된 측정 가능한 결과를 충족합니다.
- [ ] 구현 세부 사항이 사양에 유출되지 않음

## 메모

- 불완전하다고 표시된 항목은 `$speckit-clarify` 또는 `$speckit-plan` 이전에 사양 업데이트가 필요합니다.
      ```

b. **검증 확인 실행**: 각 체크리스트 항목에 대해 사양을 검토합니다.
- 각 항목에 대해 통과 또는 실패 여부를 결정합니다.
- 발견된 문서별 문제(관련 사양 섹션 인용)

c. **검증 결과 처리**:

- **모든 항목이 통과된 경우**: 체크리스트를 완료로 표시하고 필수 실행 후 후크 섹션으로 진행합니다.

- **항목이 실패한 경우([NEEDS CLARIFICATION] 제외)**:
1. 실패한 항목과 구체적인 문제를 나열합니다.
2. 각 문제를 해결하기 위해 사양을 업데이트합니다.
3. 모든 항목이 통과할 때까지 유효성 검사를 다시 실행합니다(최대 3회 반복).
4. 3번의 반복 후에도 여전히 실패하는 경우 체크리스트 메모에 남은 문제를 기록하고 사용자에게 경고합니다.

- **[NEEDS CLARIFICATION] 마커가 남아 있는 경우**:
1. 사양에서 모든 [NEEDS CLARIFICATION: ...] 마커를 추출합니다.
2. **한계 확인**: 3개 이상의 마커가 있는 경우 가장 중요한 3개만 유지하고(scope/security/UX 영향으로) 나머지에 대해서는 정보에 입각한 추측을 하세요.
3. 필요한 각 설명(최대 3개)에 대해 다음 형식으로 사용자에게 옵션을 제공합니다.

           ```markdown
## 질문 [N]: [주제]

**컨텍스트**: [관련 사양 섹션 인용]

**우리가 알아야 할 사항**: [NEEDS CLARIFICATION 마커의 구체적인 질문]

**제안 답변**:

| 옵션 | 답변 | 의미 |
           |--------|--------|--------------|
| A | [첫 번째 제안 답변] | [이 기능의 의미] |
| B | [두 번째 제안 답변] | [이 기능의 의미] |
| C | [세 번째 제안 답변] | [이 기능의 의미] |
| 사용자 정의 | 자신만의 답변 제공 | [사용자 정의 입력 제공 방법 설명] |

**귀하의 선택**: _[사용자 응답을 기다립니다]_
           ```

4. **중요 - 테이블 형식**: 마크다운 테이블의 형식이 올바른지 확인하세요.
- 파이프가 정렬된 상태에서 일관된 간격을 사용합니다.
- 각 셀에는 내용 주위에 공백이 있어야 합니다. `|Content|`가 아닌 `| Content |`
- 헤더 구분 기호에는 대시가 3개 이상 있어야 합니다: `|--------|`
- 마크다운 미리보기에서 테이블이 올바르게 렌더링되는지 테스트합니다.
5. 질문에 순차적으로 번호를 매깁니다(Q1, Q2, Q3 - 최대 총 3개).
6. 답변을 기다리기 전에 모든 질문을 함께 제시하세요.
7. 사용자가 모든 질문에 대해 자신이 선택한 항목으로 응답할 때까지 기다립니다(예: "Q1: A, Q2: 맞춤 - [세부정보], Q3: B")
8. 각 [NEEDS CLARIFICATION] 마커를 사용자가 선택하거나 제공한 답변으로 교체하여 사양을 업데이트합니다.
9. 모든 설명이 해결된 후 유효성 검사를 다시 실행합니다.

디. **체크리스트 업데이트**: 각 검증 반복 후 현재 pass/fail 상태로 체크리스트 파일을 업데이트합니다.

## 필수 실행 후 후크

**사용자에게 완료를 보고하기 전에 이 섹션을 완료해야 합니다.**

프로젝트 루트에 `.specify/extensions.yml`가 있는지 확인하세요.
- 존재하지 않거나 `hooks.after_specify`에 등록된 Hook이 없는 경우 Completion Report로 건너뜁니다.
- 존재하는 경우 이를 읽고 `hooks.after_specify` 키 아래에서 항목을 찾습니다.
- YAML을 구문 분석할 수 없거나 유효하지 않은 경우 후크 검사를 자동으로 건너뛰고 완료 보고서를 계속 진행합니다.
- `enabled`가 명시적으로 `false`인 후크를 필터링합니다. `enabled` 필드가 없는 후크는 기본적으로 활성화된 것으로 처리합니다.
- 나머지 각 후크에 대해 후크 `condition` 표현식을 해석하거나 평가하려고 **하지 마세요**.
- 후크에 `condition` 필드가 없거나 null/empty인 경우 후크를 실행 가능한 것으로 처리합니다.
- 후크가 비어 있지 않은 `condition`를 정의하는 경우 후크를 건너뛰고 조건 평가를 HookExecutor 구현에 맡깁니다.
- 후크 명령 이름으로 명령 호출을 구성할 때 점(`.`)을 하이픈(`-`)으로 바꾸십시오. 예를 들어 `speckit.git.commit` → `$speckit-git-commit`입니다.
- 각 실행 가능한 후크에 대해 `optional` 플래그를 기반으로 다음을 출력합니다.
- **필수 후크**(`optional: false`) — **각 필수 후크에 대해 `EXECUTE_COMMAND:`를 내보내야 합니다**:
    ```
## 확장 후크

**자동 후크**: {extension}
실행 중: `/{command}`
EXECUTE_COMMAND: {command}
    ```
위의 블록을 출력한 후에는 실제로 후크를 호출하고 계속하기 전에 완료될 때까지 기다려야 합니다. 이 에이전트/세션에서 직접 명령을 실행하는 것과 동일한 방식으로 실행합니다(호출은 위에 표시된 리터럴 `{command}` ID와 다를 수 있습니다. 예를 들어 기술 모드 에이전트는 이를 `/skill:speckit-...` 또는 `$speckit-...`로 실행합니다). 블록을 출력하는 것만으로는 후크가 실행되지 않습니다.
- **후크 옵션**(`optional: true`):
    ```
## 확장 후크

**후크 옵션**: {extension}
명령: `/{command}`
설명: {description}

프롬프트: {prompt}
실행하려면: `/{command}`
    ```

## 빠른 지침

- 사용자에게 필요한 **무엇**과 **이유**에 집중하세요.
- 구현 방법을 피하세요(기술 스택, API, 코드 구조 없음).
- 개발자가 아닌 비즈니스 이해관계자를 위해 작성되었습니다.
- 사양에 포함된 체크리스트를 만들지 마세요. 그것은 별도의 명령이 될 것입니다.

### 섹션 요구 사항

- **필수 섹션**: 모든 기능에 대해 완료해야 합니다.
- **선택 섹션**: 기능과 관련된 경우에만 포함
- 해당 부분이 적용되지 않는 경우 전체 삭제("N/A"로 남겨두지 않음)

### AI 세대를 위해

사용자 프롬프트에서 이 사양을 생성하는 경우:

1. **정보를 바탕으로 추측**: 상황, 업계 표준, 공통 패턴을 사용하여 격차를 메우세요.
2. **가정 문서화**: 가정 섹션에 합리적인 기본값을 기록합니다.
3. **설명 제한**: 최대 3개의 [NEEDS CLARIFICATION] 마커 - 다음과 같은 중요한 결정에만 사용하세요.
- 기능 범위나 사용자 경험에 큰 영향을 미칩니다.
- 서로 다른 의미를 지닌 다양한 합리적인 해석을 가짐
- 합리적인 기본값이 없습니다.
4. **명확한 설명 우선순위**: 범위 > security/privacy > 사용자 경험 > 기술 세부정보
5. **테스터처럼 생각하기**: 모든 모호한 요구사항은 "테스트 가능하고 명확한" 체크리스트 항목에 실패해야 합니다.
6. **명확한 설명이 필요한 공통 영역**(합리적인 기본값이 없는 경우에만):
- 기능 범위 및 경계(include/exclude 특정 사용 사례)
- 사용자 유형 및 권한(여러 가지 상충되는 해석이 가능한 경우)
- Security/compliance 요구 사항(legally/financially가 중요한 경우)

**합리적인 기본값의 예**(이것에 대해서는 묻지 마세요):

- 데이터 보존: 해당 도메인에 대한 업계 표준 관행
- 성능 목표: 명시되지 않는 한 표준 web/mobile 앱 기대치
- 오류 처리: 적절한 대체 조치가 포함된 사용자 친화적인 메시지
- 인증 방법: 표준 세션 기반 또는 웹 앱용 OAuth2
- 통합 패턴: 프로젝트에 적합한 패턴 사용(웹 서비스용 REST/GraphQL, 라이브러리용 함수 호출, 도구용 CLI 인수 등)

### 성공 기준 지침

성공 기준은 다음과 같아야 합니다.

1. **측정 가능**: 특정 지표(시간, 백분율, 개수, 비율)를 포함합니다.
2. **기술에 구애받지 않음**: 프레임워크, 언어, 데이터베이스 또는 도구에 대한 언급이 없습니다.
3. **사용자 중심**: 시스템 내부가 아닌 user/business 관점에서 결과를 설명합니다.
4. **검증 가능**: 구현 세부 사항을 몰라도 tested/validated가 될 수 있습니다.

**좋은 예**:

- "사용자는 3분 이내에 결제를 완료할 수 있습니다."
- "시스템은 10,000명의 동시 사용자를 지원합니다"
- "검색의 95%가 1초 이내에 결과를 반환합니다."
- "작업 완료율이 40% 향상됩니다"

**나쁜 예**(구현 중심):

- "API 응답 시간은 200ms 미만입니다."(너무 기술적이므로 "사용자가 즉시 결과 확인"을 사용하세요.)
- "데이터베이스는 1000TPS를 처리할 수 있습니다"(구현 세부정보, 사용자 측 측정항목 사용)
- "React 구성 요소가 효율적으로 렌더링됩니다"(프레임워크별)
- "80% 이상의 Redis 캐시 적중률"(기술별)
