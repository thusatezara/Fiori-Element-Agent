## 사용자 입력

```text
$ARGUMENTS
```

진행하기 전에 **반드시** 사용자 입력을 고려해야 합니다(비어 있지 않은 경우).

## 실행 전 검사

**확장 후크 확인(작업에서 이슈로 변환하기 전)**:
- 프로젝트 루트에 `.specify/extensions.yml`가 존재하는지 확인하세요.
- 존재하는 경우 이를 읽고 `hooks.before_taskstoissues` 키 아래 항목을 찾습니다.
- YAML을 파싱할 수 없거나 유효하지 않은 경우 후크 검사를 자동으로 건너뛰고 정상적으로 계속 진행합니다.
- `enabled`가 명시적으로 `false`인 후크를 필터링합니다. `enabled` 필드가 없는 후크는 기본적으로 활성화된 것으로 처리합니다.
- 나머지 각 후크에 대해 후크 `condition` 표현식을 해석하거나 평가하려고 **하지 마세요**.
- 후크에 `condition` 필드가 없거나 null/empty인 경우 후크를 실행 가능한 것으로 처리합니다.
- 후크가 비어 있지 않은 `condition`를 정의하는 경우 후크를 건너뛰고 조건 평가를 HookExecutor 구현에 맡깁니다.
- 후크 명령 이름으로 명령 호출을 구성할 때 점(`.`)을 하이픈(`-`)으로 바꾸십시오. 예를 들어 `speckit.git.commit` → `$speckit-git-commit`입니다.
- 각 실행 가능한 후크에 대해 `optional` 플래그를 기반으로 다음을 출력합니다.
- **후크 옵션**(`optional: true`):
    ```
## 확장 후크

**옵션 프리훅**: {extension}
명령: `/{command}`
설명: {description}

프롬프트: {prompt}
실행하려면: `/{command}`
    ```
- **필수 후크** (`optional: false`):
    ```
## 확장 후크

**자동 프리훅**: {extension}
실행 중: `/{command}`
EXECUTE_COMMAND: {command}

개요로 진행하기 전에 후크 명령의 결과를 기다리십시오.
    ```
위의 블록을 출력한 후에는 실제로 후크를 호출하고 계속하기 전에 완료될 때까지 기다려야 합니다. 이 에이전트/세션에서 직접 명령을 실행하는 것과 동일한 방식으로 실행합니다(호출은 위에 표시된 리터럴 `{command}` ID와 다를 수 있습니다. 예를 들어 기술 모드 에이전트는 이를 `/skill:speckit-...` 또는 `$speckit-...`로 실행합니다). 블록을 출력하는 것만으로는 후크가 실행되지 않습니다.
- 등록된 Hook이 없거나 `.specify/extensions.yml`가 존재하지 않는 경우 자동으로 건너뜁니다.

## 개요

1. repo 루트에서 `.specify/scripts/powershell/check-prerequisites.ps1 -Json -RequireTasks -IncludeTasks`를 실행하고 FEATURE_DIR 및 AVAILABLE_DOCS 목록을 구문 분석합니다. 모든 경로는 절대 경로여야 합니다. "I'm Groot"와 같이 인수에 작은따옴표를 사용하려면 이스케이프 구문을 사용하세요. 예: 'I'\''m Groot'(또는 가능하면 큰따옴표: "I'm Groot").
1. **존재하는 경우**: 프로젝트 원칙 및 거버넌스 제약 조건에 대해 `.specify/memory/constitution.md`를 로드합니다.
1. 실행된 스크립트에서 **작업** 경로를 추출합니다.
1. 다음을 실행하여 Git 원격을 가져옵니다.

```bash
git config --get remote.origin.url
```

> [!주의]
> 리모컨이 GITHUB URL인 경우에만 다음 단계로 진행하세요.

1. **중복 제거를 위해 기존 문제 가져오기**: 무엇이든 생성하기 전에 `tasks.md`에서 처리할 작업 ID 세트를 만듭니다(각각은 `T` 뒤에 **최소** 세 자리 숫자가 옵니다. 예: `T001` — `$speckit-converge`는 `T{M+1:03d}`로 새 ID를 할당합니다. 이는 상한선이 아닌 바닥선입니다. 따라서 파일에 999개가 넘는 작업이 있으면 ID는 4자리 이상입니다. 그런 다음 GitHub MCP 서버의 `list_issues` 도구를 사용하여 이미 해당 ID와 관련된 문제를 찾으세요. `state` 값을 생략하면 도구가 공개 문제와 종료 문제를 모두 반환하므로 값을 전달하지 마세요. 호출 수를 줄이도록 `perPage: 100`를 요청하고 도구는 커서 기반 페이지 매김을 사용하므로 `after` 매개변수(이전 응답의 `endCursor` 사용)로 페이지를 요청합니다. 각 이슈 제목에 대해 작업 ID 패턴 `\bT\d{3,}\b`(`{3,}`는 4자리 이상의 ID를 허용합니다. `\d{3}`를 사용하면 `T1000`를 포함하는 제목은 전혀 일치하지 않습니다. 왜냐하면 후행 `\b`는 두 자리 사이에 들어갈 수 없기 때문입니다. 중복 제거되거나 생성되지 않습니다. 단어 경계는 여전히 `ST001`와 같은 토큰의 일치를 중지하고 `T100`가 `T1000` 내에서 일치할 수 없도록 강제 실행합니다. 이는 또한 `T001 ...`, `T001: ...` 또는 `[T001] ...`로 작성된 제목을 인식하고 작업 ID 중 하나와 일치하면 표시합니다. ID에는 이미 문제가 있는 것 같습니다. 모든 작업 ID가 일치하거나 더 이상 페이지가 없으면 페이지 매김을 중지하십시오. 그러면 모든 작업 ID가 고려된 후에 전체 저장소의 문제 기록을 계속 가져오는 일이 발생하지 않습니다. 이는 문제 기록이 큰 저장소에 대한 호출 수를 제한하고 `tasks.md`가 재생성되거나 스킬이 다시 호출된 후 명령이 다시 실행될 때 중복을 방지합니다.
1. 목록의 각 작업에 대해 GitHub MCP 서버를 사용하여 Git 원격을 대표하는 저장소에 새 문제를 생성합니다. `tasks.md`의 작업 줄은 마크다운 확인란으로 시작하므로 먼저 선행 `- [ ]`(및 모든 `[P]` / `[US#]` 마커)를 제거하여 작업 ID와 해당 설명을 복구합니다. `T001: <description>` 형식의 단일 표준 제목으로 이슈를 생성합니다. ID를 한 번 작성한 다음 작업 설명을 입력합니다(예를 들어 `- [ ] T001 Create project structure` 줄은 제목 `T001: Create project structure`가 됩니다).
- 이전 단계의 기존 이슈 세트에 ID가 이미 존재하는 작업을 **건너뛰**하고 이를 보고합니다(예: `T001 already has an issue, skipping`).
- 아직 일치하는 이슈가 없는 작업에 대해서만 이슈를 생성하세요.

> [!주의]
> 어떠한 경우에도 원격 URL와 일치하지 않는 리포지토리에서 문제를 생성하지 마십시오.
