## 사용자 입력

```text
$ARGUMENTS
```

진행하기 전에 **반드시** 사용자 입력을 고려해야 합니다(비어 있지 않은 경우).

## 실행 전 검사

**확장 후크 확인(명확화 전)**:
- 프로젝트 루트에 `.specify/extensions.yml`가 존재하는지 확인하세요.
- 존재하는 경우 이를 읽고 `hooks.before_clarify` 키 아래 항목을 찾습니다.
- YAML을 파싱할 수 없거나 유효하지 않은 경우 후크 검사를 자동으로 건너뛰고 정상적으로 계속 진행합니다.
- `enabled`가 명시적으로 `false`인 후크를 필터링합니다. `enabled` 필드가 없는 후크는 기본적으로 활성화된 것으로 처리합니다.
- 나머지 각 후크에 대해 후크 `condition` 표현식을 해석하거나 평가하려고 **하지 마세요**.
- 후크에 `condition` 필드가 없거나 null/empty인 경우 후크를 실행 가능한 것으로 처리합니다.
- 후크가 비어 있지 않은 `condition`를 정의하는 경우 후크를 건너뛰고 조건 평가를 HookExecutor 구현에 맡깁니다.
- 후크 명령 이름으로 명령 호출을 구성할 때 점(`.`)을 하이픈(`-`)으로 바꾸십시오. 예를 들어 `speckit.git.commit` → `$speckit-git-commit`입니다.
- 각 실행 가능한 후크에 대해 `optional` 플래그를 기반으로 다음을 출력합니다.
- **후크 옵션**(`optional: true`):
    ```
## 확장 후크

**옵션 프리훅**: {extension}
명령: `/{command}`
설명: {description}

프롬프트: {prompt}
실행하려면: `/{command}`
    ```
- **필수 후크** (`optional: false`):
    ```
## 확장 후크

**자동 프리훅**: {extension}
실행 중: `/{command}`
EXECUTE_COMMAND: {command}

개요로 진행하기 전에 후크 명령의 결과를 기다리십시오.
    ```
위의 블록을 출력한 후에는 실제로 후크를 호출하고 계속하기 전에 완료될 때까지 기다려야 합니다. 이 에이전트/세션에서 직접 명령을 실행하는 것과 동일한 방식으로 실행합니다(호출은 위에 표시된 리터럴 `{command}` ID와 다를 수 있습니다. 예를 들어 기술 모드 에이전트는 이를 `/skill:speckit-...` 또는 `$speckit-...`로 실행합니다). 블록을 출력하는 것만으로는 후크가 실행되지 않습니다.
- 등록된 Hook이 없거나 `.specify/extensions.yml`가 존재하지 않는 경우 자동으로 건너뜁니다.

## 개요

목표: 활성 기능 사양에서 모호함이나 누락된 결정 지점을 감지 및 줄이고 사양 파일에 직접 설명을 기록합니다.

참고: 이 설명 워크플로는 `$speckit-plan`를 호출하기 전에 실행(및 완료)될 것으로 예상됩니다. 사용자가 설명을 건너뛰고 있다고 명시적으로 언급하는 경우(예: 탐색적 급증) 계속 진행할 수 있지만 다운스트림 재작업 위험이 증가한다는 점을 경고해야 합니다.

실행 단계:

1. 저장소 루트에서 `.specify/scripts/powershell/check-prerequisites.ps1 -Json -PathsOnly`를 **한 번** 실행합니다(`--json --paths-only` 모드 / `-Json -PathsOnly` 결합). 최소 JSON 페이로드 필드를 구문 분석합니다.
- `FEATURE_DIR`
- `FEATURE_SPEC`
- (향후 연결 흐름을 위해 선택적으로 `IMPL_PLAN`, `TASKS`를 캡처합니다.)
- JSON 구문 분석에 실패하면 중단하고 사용자에게 `$speckit-specify`를 다시 실행하거나 기능 분기 환경을 확인하도록 지시합니다.
- "I'm Groot"와 같이 인수에 작은따옴표를 사용하려면 이스케이프 구문을 사용하세요. 예: 'I'\''m Groot'(또는 가능하면 큰따옴표: "I'm Groot").

2. **존재하는 경우**: 프로젝트 원칙 및 거버넌스 제약 조건에 대해 `.specify/memory/constitution.md`를 로드합니다.

3. 현재 사양 파일을 로드합니다. 이 분류법을 사용하여 구조화된 모호성 및 적용 범위 스캔을 수행합니다. 각 카테고리에 대해 상태를 명확함/일부/누락으로 표시합니다. 우선순위 지정에 사용되는 내부 적용 범위 맵을 생성합니다(질문이 없는 한 원시 맵을 출력하지 않음).

- 사용자 역할 / 페르소나 차별화

4. 우선순위가 지정된 후보자 설명 질문 대기열(최대 5개)을 (내부적으로) 생성합니다. 한 번에 모두 출력하지 마십시오. 다음 제약조건을 적용합니다.
- 전체 세션에 걸쳐 최대 5개의 질문이 가능합니다.
- 각 질문은 다음 중 하나로 답할 수 있어야 합니다.
- 짧은 객관식 선택(2~5개의 서로 다른, 상호 배타적인 옵션), 또는
- 한 단어/짧은 문구로 된 답변(명시적으로 제한: "답변은 <=5 단어").
- 답변이 아키텍처, 데이터 모델링, 작업 분해, 테스트 설계, UX 동작, 운영 준비 또는 규정 준수 검증에 실질적으로 영향을 미치는 질문만 포함합니다.
- 카테고리 적용 범위 균형 보장: 영향이 가장 큰 미해결 카테고리를 먼저 포함하려고 시도합니다. 하나의 큰 영향 영역(예: 보안 태세)이 해결되지 않은 경우 두 개의 낮은 영향 질문을 하지 마십시오.
- 이미 답변된 질문, 사소한 스타일 선호 사항 또는 계획 수준 실행 세부 정보를 제외합니다(정확성을 차단하지 않는 한).
- 다운스트림 재작업 위험을 줄이거나 잘못 정렬된 승인 테스트를 방지하는 설명을 선호합니다.
- 해결되지 않은 항목이 5개 이상인 경우 (Impact * Uncertainty) 휴리스틱으로 상위 5개 항목을 선택합니다.

5. 순차적 질문 루프(대화형):
- 한 번에 정확히 하나의 질문만 제시하세요.
- **질문 작성 품질(MC 또는 단답형 모든 질문에 적용):**
- `**Question:**`로 시작하고 `?`로 끝나는 전체 의문문이 이어집니다. `?` 앞의 질문 텍스트는 그 자체로 의미가 있어야 합니다.
- 주제 라벨, 섹션 제목, 요구사항 ID를 질문 자체로 사용하지 마세요. 예를 들어, `Acceptance device/runtime matrix (FR-023)`는 INVALID입니다. 이는 질문이 아니라 레이블입니다.
- `?` 뒤에 허용되는 유일한 접미사는 선택적 괄호 안에 있는 requirement/question ID입니다. 정확한 형식: `**Question:** <interrogative>?` 또는 `**Question:** <interrogative>? (FR-023)`. `?` 앞에 ID를 넣지 말고 ID(단독으로 또는 주제 레이블과 함께)를 전체 프롬프트로 사용하지 마십시오.
- 질문 라인 바로 뒤, recommendation/options. 앞에 일반 언어로 된 "왜 중요한가" 문장(수락 또는 배송에 대한 지분)을 추가합니다.
- 일상적인 표현을 사용하세요. 같은 문장에 정의된 경우에만 전문 용어를 소개합니다. 자가 점검: Spec Kit를 모르는 독자는 질문 라인에서만 답변할 수 있어야 합니다. 간결한 것은 괜찮습니다. 비밀스러운 라벨은 그렇지 않습니다.
- 객관식 질문의 경우:
- **모든 옵션을 분석**하고 다음을 기준으로 **가장 적합한 옵션**을 결정합니다.
- 프로젝트 유형에 대한 모범 사례
- 유사한 구현의 공통 패턴
- 위험 감소(보안, 성능, 유지 관리성)
- 사양에 표시되는 명시적인 프로젝트 목표 또는 제약 조건과의 일치
- 명확한 추론과 함께 **권장 옵션을 눈에 띄게** 상단에 제시하세요(이 옵션이 최선의 선택인 이유를 1~2 문장으로 설명).
- 형식: `**Recommended:** Option [X] - <reasoning>`
- 그런 다음 모든 옵션을 Markdown 테이블로 렌더링합니다.

| 옵션 | 설명 |
       |--------|-------------|
| A | <Option A description> |
| B | <Option B description> |
| C | <Option C description> (필요에 따라 D/E를 최대 5개까지 추가) |
| 짧은 | 다른 짧은 답변 제공(<=5단어)(자유 형식 대안이 적절한 경우에만 포함) |

- 테이블 뒤에 다음을 추가합니다: `You can reply with the option letter (e.g., "A"), accept the recommendation by saying "yes" or "recommended", or provide your own short answer.`
- 단답형(의미 있는 개별 옵션 없음):
- 모범 사례와 맥락을 바탕으로 **제안 답변**을 제공하세요.
- 형식: `**Suggested:** <your proposed answer> - <brief reasoning>`
- 그런 다음 출력: `Format: Short answer (<=5 words). You can accept the suggestion by saying "yes" or "suggested", or provide your own answer.`
- 사용자가 응답한 후:
- 사용자가 "예", "권장" 또는 "제안"으로 응답하는 경우 이전에 언급한 recommendation/suggestion를 답변으로 사용하세요.
- 그렇지 않은 경우 답변이 하나의 옵션에 매핑되는지 또는 <=5 단어 제약 조건에 맞는지 확인하세요.
- 모호한 경우 빠른 명확성을 요청합니다(계산은 여전히 동일한 질문에 속하므로 진행하지 않음).
- 만족스러우면 작업 메모리에 기록하고(아직 디스크에 쓰지 않음) 대기 중인 다음 질문으로 이동합니다.
- 다음과 같은 경우에는 더 이상 질문하지 마세요.
- 모든 중요한 모호성이 조기에 해결되었습니다(나머지 대기열 항목이 불필요해짐). 또는
- 사용자 신호 완료("완료", "양호", "더 이상") 또는
- 5개의 질문에 도달했습니다.
- 향후 대기 중인 질문을 미리 공개하지 마세요.
- 시작할 때 유효한 질문이 없으면 심각한 모호성이 없는지 즉시 보고하십시오.

6. 각 승인 답변 후 통합(증분 업데이트 접근 방식):
- 사양(시작 시 한 번 로드됨)과 원시 파일 콘텐츠의 메모리 내 표현을 유지합니다.
- 이번 세션의 첫 번째 통합 답변:
- `## Clarifications` 섹션이 있는지 확인합니다(누락된 경우 사양 템플릿당 최고 수준 contextual/overview 섹션 바로 뒤에 생성).
- 그 아래에 오늘의 `### Session YYYY-MM-DD` 부제목을 만듭니다(없을 경우).
- 승인 후 즉시 글머리 기호 추가: `- Q: <question> → A: <final answer>`.
- 그런 다음 가장 적절한 섹션에 설명을 즉시 적용하십시오.
- 기능적 모호성 → 기능적 요구사항에 글머리 기호를 업데이트하거나 추가합니다.
- 사용자 상호 작용/행위자 구별 → 명확한 역할, 제약 또는 시나리오를 사용하여 사용자 스토리 또는 행위자 하위 섹션(있는 경우)을 업데이트합니다.
- 데이터 모양/엔터티 → 순서를 유지하면서 데이터 모델 업데이트(필드, 유형, 관계 추가) 제약 조건을 간결하게 추가했습니다.
- 비기능적 제약 → 성공 기준 > 측정 가능한 결과에서 Add/modify 측정 가능한 기준(모호한 형용사를 측정 기준 또는 명시적 목표로 변환).
- 엣지 케이스/네거티브 흐름 → 엣지 케이스/오류 처리 아래에 새 글머리 기호를 추가합니다(또는 템플릿이 자리 표시자를 제공하는 경우 해당 하위 섹션을 만듭니다).

6. 업데이트된 체크리스트 파일을 저장합니다. **상태가 변경된 확인란 줄의 `[ ]`/`[x]` 마커 부분만 토글합니다.** 다른 모든 파일 콘텐츠(제목, 메타데이터, 메모, 줄 순서, 공백)는 시끄러운 차이를 피하기 위해 변경되지 않은 상태로 유지되어야 합니다.

## 필수 실행 후 후크

**사용자에게 완료를 보고하기 전에 이 섹션을 완료해야 합니다.**

프로젝트 루트에 `.specify/extensions.yml`가 있는지 확인하세요.
- 존재하지 않거나 `hooks.after_clarify`에 등록된 Hook이 없는 경우 Completion Report로 건너뜁니다.
- 존재하는 경우 이를 읽고 `hooks.after_clarify` 키 아래에서 항목을 찾습니다.
- YAML을 구문 분석할 수 없거나 유효하지 않은 경우 후크 검사를 자동으로 건너뛰고 완료 보고서를 계속 진행합니다.
- `enabled`가 명시적으로 `false`인 후크를 필터링합니다. `enabled` 필드가 없는 후크는 기본적으로 활성화된 것으로 처리합니다.
- 나머지 각 후크에 대해 후크 `condition` 표현식을 해석하거나 평가하려고 **하지 마세요**.
- 후크에 `condition` 필드가 없거나 null/empty인 경우 후크를 실행 가능한 것으로 처리합니다.
- 후크가 비어 있지 않은 `condition`를 정의하는 경우 후크를 건너뛰고 조건 평가를 HookExecutor 구현에 맡깁니다.
- 후크 명령 이름으로 명령 호출을 구성할 때 점(`.`)을 하이픈(`-`)으로 바꾸십시오. 예를 들어 `speckit.git.commit` → `$speckit-git-commit`입니다.
- 각 실행 가능한 후크에 대해 `optional` 플래그를 기반으로 다음을 출력합니다.
- **필수 후크**(`optional: false`) — **각 필수 후크에 대해 `EXECUTE_COMMAND:`를 내보내야 합니다**:
    ```
## 확장 후크

**자동 후크**: {extension}
실행 중: `/{command}`
EXECUTE_COMMAND: {command}
    ```
위의 블록을 출력한 후에는 실제로 후크를 호출하고 계속하기 전에 완료될 때까지 기다려야 합니다. 이 에이전트/세션에서 직접 명령을 실행하는 것과 동일한 방식으로 실행합니다(호출은 위에 표시된 리터럴 `{command}` ID와 다를 수 있습니다. 예를 들어 기술 모드 에이전트는 이를 `/skill:speckit-...` 또는 `$speckit-...`로 실행합니다). 블록을 출력하는 것만으로는 후크가 실행되지 않습니다.
- **후크 옵션**(`optional: true`):
    ```
## 확장 후크

**후크 옵션**: {extension}
명령: `/{command}`
설명: {description}

프롬프트: {prompt}
실행하려면: `/{command}`
    ```
