## 사용자 입력

```text
$ARGUMENTS
```

진행하기 전에 **반드시** 사용자 입력을 고려해야 합니다(비어 있지 않은 경우).

## 실행 전 검사

**확장 후크 확인(분석 전)**:
- 프로젝트 루트에 `.specify/extensions.yml`가 존재하는지 확인하세요.
- 존재하는 경우 이를 읽고 `hooks.before_analyze` 키 아래 항목을 찾습니다.
- YAML을 파싱할 수 없거나 유효하지 않은 경우 후크 검사를 자동으로 건너뛰고 정상적으로 계속 진행합니다.
- `enabled`가 명시적으로 `false`인 후크를 필터링합니다. `enabled` 필드가 없는 후크는 기본적으로 활성화된 것으로 처리합니다.
- 나머지 각 후크에 대해 후크 `condition` 표현식을 해석하거나 평가하려고 **하지 마세요**.
- 후크에 `condition` 필드가 없거나 null/empty인 경우 후크를 실행 가능한 것으로 처리합니다.
- 후크가 비어 있지 않은 `condition`를 정의하는 경우 후크를 건너뛰고 조건 평가를 HookExecutor 구현에 맡깁니다.
- 후크 명령 이름으로 명령 호출을 구성할 때 점(`.`)을 하이픈(`-`)으로 바꾸십시오. 예를 들어 `speckit.git.commit` → `$speckit-git-commit`입니다.
- 각 실행 가능한 후크에 대해 `optional` 플래그를 기반으로 다음을 출력합니다.
- **후크 옵션**(`optional: true`):
    ```
## 확장 후크

**옵션 프리훅**: {extension}
명령: `/{command}`
설명: {description}

프롬프트: {prompt}
실행하려면: `/{command}`
    ```
- **필수 후크** (`optional: false`):
    ```
## 확장 후크

**자동 프리훅**: {extension}
실행 중: `/{command}`
EXECUTE_COMMAND: {command}

목표로 진행하기 전에 후크 명령의 결과를 기다리세요.
    ```
위의 블록을 출력한 후에는 실제로 후크를 호출하고 계속하기 전에 완료될 때까지 기다려야 합니다. 이 에이전트/세션에서 직접 명령을 실행하는 것과 동일한 방식으로 실행합니다(호출은 위에 표시된 리터럴 `{command}` ID와 다를 수 있습니다. 예를 들어 기술 모드 에이전트는 이를 `/skill:speckit-...` 또는 `$speckit-...`로 실행합니다). 블록을 출력하는 것만으로는 후크가 실행되지 않습니다.
- 등록된 Hook이 없거나 `.specify/extensions.yml`가 존재하지 않는 경우 자동으로 건너뜁니다.

## 목표

구현하기 전에 세 가지 핵심 아티팩트(`spec.md`, `plan.md`, `tasks.md`) 전반에 걸쳐 불일치, 중복, 모호함 및 명세 부족 항목을 식별합니다. 이 명령은 `$speckit-tasks`가 완전한 `tasks.md`를 성공적으로 생성한 후에만 실행되어야 합니다.

## 운영 제약

**엄격한 읽기 전용**: 파일을 수정하지 **마세요**. 구조화된 분석 보고서를 출력합니다. 선택적 수정 계획을 제공합니다(후속 편집 명령을 수동으로 호출하기 전에 사용자가 명시적으로 승인해야 함).

**헌법의 권위**: 프로젝트 구성(`.specify/memory/constitution.md`)은 이 분석 범위 내에서 **협상 불가능**입니다. 헌법 충돌은 자동으로 CRITICAL로 분류되며 원칙을 희석하거나 재해석하거나 조용히 무시하는 것이 아니라 사양, 계획 또는 작업의 조정이 필요합니다. 원칙 자체를 변경해야 하는 경우 `$speckit-analyze` 외부에서 별도의 명시적인 헌법 업데이트를 통해 이루어져야 합니다.

## 실행 단계

### 1. 분석 컨텍스트 초기화

repo 루트에서 `.specify/scripts/powershell/check-prerequisites.ps1 -Json -RequireSpec -RequireTasks -IncludeTasks`를 한 번 실행하고 FEATURE_DIR 및 AVAILABLE_DOCS에 대해 JSON을 구문 분석합니다. 절대 경로 파생:

- SPEC = FEATURE_DIR/spec.md
- PLAN = FEATURE_DIR/plan.md
- TASKS = FEATURE_DIR/tasks.md

필수 파일이 누락된 경우 오류 메시지와 함께 중단합니다(사용자에게 누락된 필수 구성 요소 명령을 실행하도록 지시).
"I'm Groot"와 같이 인수에 작은따옴표를 사용하려면 이스케이프 구문을 사용하세요. 예: 'I'\''m Groot'(또는 가능하면 큰따옴표: "I'm Groot").

### 2. 아티팩트 로드(점진적 공개)

각 아티팩트에서 필요한 최소한의 컨텍스트만 로드합니다.

**spec.md에서:**

- Overview/Context
- 기능적 요구사항
- 성공 기준(측정 가능한 결과 - 예: 성능, 보안, 가용성, 사용자 성공, 비즈니스 영향)
- 사용자 스토리
- 엣지 케이스(있는 경우)

**plan.md에서:**

- Architecture/stack 선택
- 데이터 모델 참조
- 단계
- 기술적 제약

**tasks.md에서:**

- 작업 ID
- 설명
- 위상 그룹화
- 평행 마커 [P]
- 참조된 파일 경로

**헌법에서:**

- 원리 검증을 위해 `.specify/memory/constitution.md` 로드

### 3. 의미론적 모델 구축

내부 표현을 만듭니다(출력에 원시 아티팩트를 포함하지 않음).

- **요구사항 목록**: 각 기능 요구사항(FR-###) 및 성공 기준(SC-###)에 대해 안정적인 키를 기록합니다. 존재하는 경우 명시적인 FR-/SC- 식별자를 기본 키로 사용하고 선택적으로 가독성을 위해 명령문 슬러그도 파생시킵니다(예: "사용자가 파일을 업로드할 수 있습니다" → `user-can-upload-file`). 구축 가능한 작업(예: 로드 테스트 인프라, 보안 감사 도구)이 필요한 성공 기준 항목만 포함하고 출시 후 결과 지표 및 비즈니스 KPI(예: "지원 티켓 50% 감소")는 제외합니다.
- **사용자 story/action 인벤토리**: 승인 기준에 따른 개별 사용자 작업
- **작업 범위 매핑**: 각 작업을 하나 이상의 요구 사항 또는 스토리에 매핑합니다(키워드별 추론/ID 또는 핵심 문구와 같은 명시적 참조 패턴)
- **헌법규칙세트**: 원칙명 및 MUST/SHOULD 규범문 추출

### 4. 탐지 통과(토큰 효율적인 분석)

높은 신호 결과에 중점을 둡니다. 총 결과는 50개로 제한됩니다. 오버플로 요약에서 나머지를 집계합니다.

#### A. 중복 감지

- 거의 중복된 요구 사항 식별
- 통합을 위해 품질이 낮은 문구를 표시합니다.

#### B. 모호성 탐지

- 측정 가능한 기준이 부족한 모호한 형용사(빠름, 확장 가능, 보안, 직관적, 견고함)에 플래그를 지정합니다.
- 해결되지 않은 자리 표시자 표시(TODO, TKTK, ???, `<placeholder>` 등)

#### C. 사양 부족

- 동사가 포함되어 있지만 목적어가 누락되었거나 측정 가능한 결과가 있는 요구사항
- 승인 기준 정렬이 누락된 사용자 스토리
- spec/plan에 정의되지 않은 파일이나 구성 요소를 참조하는 작업

#### D. 헌법 정렬

- MUST 원칙과 상충되는 요구사항이나 계획 요소
- 헌법에서 필수 항목이나 품질 게이트가 누락되었습니다.

#### E. 보장 공백

- 관련 작업이 없는 요구 사항
- 매핑된 requirement/story가 없는 작업
- 구축 가능한 작업(성능, 보안, 가용성)을 요구하는 성공 기준이 작업에 반영되지 않음

#### F. 불일치

- 용어 드리프트(동일한 개념이 파일마다 다르게 명명됨)
- 계획에는 참조되었지만 사양에는 없는 데이터 엔터티(또는 그 반대)
- 작업 순서 모순(예: 종속성 메모가 없는 기본 설정 작업 이전의 통합 작업)
- 충돌하는 요구 사항(예: 하나는 Next.js가 필요하고 다른 하나는 Vue를 지정함)

### 5. 심각도 할당

이 경험적 방법을 사용하여 결과의 우선순위를 정하세요.

- **중요**: 헌법을 위반해야 하며, 핵심 사양 아티팩트가 누락되거나, 기본 기능을 차단하는 적용 범위가 0인 요구 사항을 위반해야 합니다.
- **높음**: 중복되거나 충돌하는 요구 사항, 모호한 security/performance 속성, 테스트할 수 없는 승인 기준
- **중간**: 용어 드리프트, 비기능적 작업 적용 범위 누락, 명세 부족 특수 사례
- **낮음**: Style/wording 개선, 실행 순서에 영향을 주지 않는 사소한 중복성

### 6. 컴팩트 분석 보고서 생성

다음 구조를 사용하여 마크다운 보고서(파일 쓰기 없음)를 출력합니다.

### 7. 다음 작업 제공

보고서가 끝나면 간결한 Next Actions 블록을 출력합니다.

- 심각한 문제가 있는 경우: `$speckit-implement` 이전에 해결하는 것이 좋습니다.
- LOW/MEDIUM인 경우: 사용자는 계속 진행할 수 있지만 개선 제안을 제공합니다.
- 명시적인 명령 제안 제공: 예: "세분화하여 $speckit-specify 실행", "아키텍처 조정을 위해 $speckit-plan 실행", "'성능 지표'에 대한 적용 범위를 추가하기 위해 tasks.md를 수동으로 편집"

### 8. 해결 제안

사용자에게 "상위 N개 문제에 대한 구체적인 해결 수정 사항을 제안하시겠습니까?"라고 묻습니다. (자동으로 적용하지 마세요.)

## 작동 원리

### 상황 효율성

- **최소한의 고신호 토큰**: 철저한 문서가 아닌 실행 가능한 결과에 중점을 둡니다.
- **점진적 공개**: 아티팩트를 점진적으로 로드합니다. 모든 콘텐츠를 분석에 투입하지 마세요
- **토큰 효율적인 출력**: 결과 테이블을 50개 행으로 제한합니다. 오버플로 요약
- **결정적 결과**: 변경 없이 다시 실행하면 일관된 ID와 개수가 생성되어야 합니다.

### 분석 지침

- **파일을 수정하지 마세요**(읽기 전용 분석입니다)
- **누락된 부분을 환각하지 마세요**(없는 경우 정확하게 보고하세요)
- **헌법 위반 우선순위**(항상 중요)
- **완벽한 규칙보다는 예시를 사용하세요**(일반적인 패턴이 아닌 구체적인 사례를 인용하세요)
- **제로 문제를 적절하게 보고**(적용 범위 통계와 함께 성공 보고서 보내기)

## 컨텍스트

$ARGUMENTS
